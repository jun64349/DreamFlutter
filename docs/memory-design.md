## 一、总体结构

| 部件 | 做什么 | 在哪里 |
|---|---|---|
| 记忆库 | 正式记忆条目、版本、关系、操作批次（可撤销）、快照素材、快照记录 | 后台数据库（`core.db`，新表，见第二节） |
| 记忆 Agent | 提取、分层整理、去重、冲突、快照素材、软遗忘方案（纪要 §12） | 后台进程里的内存 Pi 会话（3.4 的子 Agent 运行时），**没有执行环境**，见第五节 |
| 程序侧守门 | 作用域、权限、确认、预算、版本、事务、留痕（纪要 §12.5） | 记忆模块的操作接口：Agent 只能提「操作」，由程序校验后提交 |
| 快照组装 | 按任务从素材里选、按预算裁剪、注入 Pi 上下文、防重复防复活 | 记忆模块的 Pi 扩展（现在的 `before_agent_start` 注入改造，见第六节） |
| 调度 | 任务结束、每周、每月、每季、事件触发的整理任务；排队、预算、重试 | 记忆任务队列，复用定时模块的时钟（第七节） |
| 界面 | 记忆页（层级、状态、来源、差异、恢复）、本次用了哪些记忆、设置和仪表盘 | 窗口（0.4 外壳之后） |

原则（纪要 §3）：快照是日常起作用的主要方式；三级记忆是后台的正式记录；主 Agent 不读全库、不整理记忆；**约束靠程序，不靠提示词**。

## 二、数据结构

现有 v0.2 的表：`memories`（扁平，scope / kind / status / replaced_by）、`memory_blocks`（三块常驻）、`memory_snapshots`、`memory_extraction`。0.5 新建以下表（数据库第 9 版或之后），旧表迁移后保留只读一个版本再删（第十一节）。

### 2.1 `memory_items`：一条记忆的当前版本

| 列 | 说明（对应纪要 §5.1 的信息组） |
|---|---|
| `id` | `m_` + 随机串 |
| `version` | 整数，每次改动 +1（乐观锁，纪要 §12.5「过期候选不能覆盖最新记录」） |
| `level` | 1 近期 / 2 阶段 / 3 长期 |
| `kind` | preference 偏好 / background 背景 / experience 经验 / decision 决定 / progress 进展 / agreement 约定 / observation 观察 |
| `content` | 正文（快照里用的短句，含必要限定：版本、范围、否定、「尚未确认」） |
| `conditions` | 适用条件（可空） |
| `scope` | global / workspace / group / butterfly |
| `workspace_id` | 指向 `workspaces.id`（不是路径，纪要 §8.3「目录移动不丢关联」） |
| `group_id` | 共享组（可空） |
| `confidence` | user_explicit 用户明说 / user_confirmed 用户确认 / user_reported 用户报告 / agent_inferred Agent 推测 / verified 工具或任务结果验证 |
| `status` | candidate / active / review 待复核 / outdated 过时 / superseded 被替代 / refuted 被推翻 / archived 归档 / forgotten 软遗忘 |
| `pinned` | 常驻（原常驻块变成「被指定常驻的条目」，纪要 §9.5） |
| `retention` | normal / long（三级默认）/ locked（用户锁定永久保留） |
| `auto_ok` | 是否允许后台自动处理（用户可关） |
| `occurred_at`、`valid_from`、`valid_until` | 发生时间、有效期 |
| `last_verified_at`、`next_review_at` | 上次核对、下次复查（调度用） |
| `last_used_at`、`use_count` | 只作复核线索，**不算证据**（纪要 §11.5） |
| `created_at`、`updated_at`、`created_by` | user / main_agent / memory_agent / migration |

### 2.2 其他表

- `memory_versions(item_id, version, snapshot_json, op_id, at)`：每次改动前的整条记录，差异和单条恢复靠它。
- `memory_sources(item_id, kind, ref, excerpt, at)`：来源：`session`（会话文件 + 条目 id）、`task`、`run`、`user_edit`、`migration`；`excerpt` 只存短摘。**助手自己重复说的话不算新来源**（纪要 §6）：同一会话里 assistant 消息不作为独立证据。
- `memory_links(from_id, to_id, kind)`：`derived_from` 提炼自、`supersedes` 替代、`conflicts` 冲突、`refutes` 推翻。
- `memory_ops(id, batch_id, actor, kind, item_id, before_version, after_version, reason, cost_usd, at, undone_at)`：所有改动的留痕；一个整理任务、一次软遗忘就是一个 `batch_id`，可以整批回撤（纪要 §11.7）。
- `memory_materials(id, scope_key, item_ids, text, tokens, version, built_at, stale)`：记忆 Agent 维护的**快照素材**（按作用域预先写好的短文本块），程序按任务复用（纪要 §10.2）。条目变了，含它的素材标 `stale`。
- `memory_snapshots`：扩展现有表：加 `snapshot_id`、`task_key`、`budget`、`tokens`、`item_versions`（条目 id → 版本）、`status`（ok / degraded / failed），用于「本次用了哪些记忆」和回滚。
- `memory_jobs(id, kind, scope_key, payload, priority, status, attempts, cost_usd, error, created_at, started_at, ended_at)`：记忆 Agent 的任务队列（第七节）。
- `workspaces(id, path, created_at)`、`workspace_groups(id, name)`、`workspace_group_members`：工作区的稳定身份。路径变了（用户改名、v0.3.1 导入换电脑）只改 `path`，记忆跟着 `id` 走。v0.3.1 的路径对照表顺手更新这里。
- 删除抑制（纪要 §11.8 的「彻底删除」，0.5 只建表）：`memory_suppressions(source_ref, pattern_hash, at)`：用户要求彻底忘掉的内容，正文删除，只留不含正文的哈希，防止后台从同一来源再提取回来。

**原子性**：一个操作批次在一个 SQLite 事务里提交（`Db.transaction`），失败整批回滚（纪要 §12.5「要么完整提交」）。

## 三、层级、状态和转化（纪要 §4、§7）

- **一级**：近 14 天重点管理（已确认）。超过 14 天不自动删除，由每周整理决定提炼、保留或标记结束。
- **二级**：阶段内持续有用；每周轻量复查（只看新增、变化、冲突）、每月整理、每季回顾、事件触发。
- **三级**：长期，一般不遗忘；有新证据、用户纠正、环境变化时核对；每月轻量、每季针对、每年完整回顾。

转化由记忆 Agent **提出**、程序**校验**后提交：

| 转化 | 程序检查 |
|---|---|
| 一级 → 二级 | 有 `decision` 或独立来源 ≥ 1（不同会话），或用户确认 |
| 二级 → 三级 | 置信度是 user_* 或 verified；适用条件非空；自动执行、记入记忆日志（用户 2026-11-06 定，见第四节和十二.3） |
| 直接进三级 | 用户明说「长期记住」且范围明确 |
| 三级 → 二级 | 记录变化（op + 版本） |
| → 待复核 / 过时 / 被替代 / 被推翻 | 写 `memory_links`，旧条目退出快照但保留 |

提炼时：新条目 `derived_from` 原条目，原条目转 `archived`（退出默认调用，保留来源，可展开、可恢复）——这就是纪要 §11.2 的「自然遗忘」。同一属性的新旧信息按适用时间、作用域、证据处理，**不做「最后写入覆盖」**。

## 四、写入权限（纪要 §6，程序侧落实）

> **2026-11-06 用户改为「默认自动生效」**：「记忆的审批有点太多了有点效率低……默认自动审批记录保存下来，然后用户可以进到界面里看哪天保存了哪些记忆遗忘了哪些记忆并可以直接操作修改删除」。
>
> - 下表「要用户确认的」一列，默认改为**自动生效并记入当天的记忆日志**（新增、修改、升级、合并、到期、推翻、软遗忘都记，每条带原因、来源和「撤销」）；用户在记忆页按天查看，可直接修改、删除、恢复。
> - 程序侧的校验（作用域、版本、事务、留痕、预算）照旧；变的只是「要不要先等用户点头」。
> - 设置里留一个「写入前要我确认」开关（默认关），打开后回到下表的确认规则（类似 Hermes 的 `write_approval`）。
> - **例外**（用户 2026-11-06 定）：① 用户**锁定**的记忆后台永远不自动改，只标「待复核」并提醒；② **彻底删除**只能用户本人做；③ **工作区的记忆提升为全局**（所有工作区可见）要用户决定（隔离关系到隐私，而且不常发生）。
> - 记忆日志是自动生效的安全网，**0.5 就要有能用的最简界面**（按天列出、能改能删能撤销），完整设计在 0.11。

| 谁 | 能直接生效的 | 要用户确认的 |
|---|---|---|
| 用户（界面编辑、「记住这件事」） | 全部，立即生效，留版本 | — |
| 主 Agent（`memory_save` 工具） | `explicit=true` 且用户原话里有「记住」类表达：按指明的范围和期限保存，回执 | 推断的偏好、长期背景；扩到全局；永久保留 |
| 记忆 Agent | 一级的普通近期进展（记来源）；去重合并（不涉及三级和锁定）；状态改成待复核 | 晋升三级；全局或跨工作区共享；删除或重大改写已确认内容；软遗忘方案 |

范围不明时默认当前工作区，不扩成全局（纪要 §6）。用户刚纠正的内容立即生效（标记当前快照失效，第六节）；后台推断不覆盖用户确认过的内容（版本检查 + `confidence` 比较）。候选可以批量确认，带内容、来源、范围、理由。

## 五、记忆 Agent（纪要 §12）

- **角色卡**（`agent/roles.ts` 新增 `memory`）：没有 shell、文件、网络、搜索工具；只有读记忆库的查询工具和「提交操作」工具（`memory_propose_ops`：结构化的新增 / 更新 / 提炼 / 替代 / 状态变更 / 待确认 / 软遗忘建议，每项带证据和理由）。模型：设置里可选「记忆模型」，默认用辅助模型（标题、技能草稿用的那个），没有就用默认模型（用户 2026-11-06 定）。轮数上限 20。
- **运行和隔离**：在后台进程里以内存 Pi 会话运行（3.4 的 `openSubagentRuntime` 同一套），**不挂任何执行环境**——它碰不到本机文件，也碰不到蝶君的沙箱，比沙箱隔离更严。纪要 §3.4 说的「用户已有的隔离与存储方案」= 蝶君补充第 4 节，那一节约束的是能执行命令的 Agent；记忆 Agent 不执行命令，所以只需要做到：数据只在后台数据库里，输入只给本次授权范围内的内容。**用户 2026-11-06 确认符合原意。**
- **输入**（纪要 §12.3）：任务类型、允许的作用域、增量来源（新消息、任务结果的摘录，按 `memory_extraction` 的游标）、相关现有条目（只给本范围的，带 `version`）、冲突和候选列表、快照需求、本次预算和允许的操作种类。
- **输出**（纪要 §12.4）：`memory_propose_ops` 的 JSON。程序逐项校验：作用域、权限（第四节）、目标版本是否还是最新、预算；不合格的项拒绝并写原因，合格的在一个事务里提交成一个批次；要确认的转成候选。
- **程序侧约束对照**（纪要 §12.5）：作用域和授权 → 每个操作检查 `scope`/`workspace_id`；重要更新 → 第四节表；版本 → `version` 乐观锁；原子 → 事务；确认时重查版本 → 候选记 `base_version`，确认时不等就提示「已有更新，请重新看」；预算 → 记忆任务的模型调用经网关计费，记在 `usage_records`，来源标 `memory`，重试也算；不能提权改预算 → 工具里没有这些操作；失败 → 不提交，任务记 `failed` 和原因，有限重试（第七节）。

## 六、快照在 Pi 上下文里怎么组装（纪要 §9、§10）

### 6.1 预算（纪要 §9.3，初版参数）

```text
本次记忆预算 = min(用户上限（默认 2000 token）, 模型上下文窗口 × 3%, (窗口 − 非记忆内容 − 执行预留) × 15%)
执行预留 = 模型最大输出 + 8000 token（工具交互）
```

配额（2000 时）：常驻 300 + 相关记忆 1400（一级 40% / 二级 35% / 三级 25%，软配额，缺的让给别层）+ 补充 300。常驻条目超过自己的份额时**提示用户精简**，不截断、不偷偷不计入。token 用模型实际的计数（网关记录的 usage）回校估算值，估算时留 10% 余量。

### 6.2 选择

程序做（不调模型）：按作用域过滤（全局里被当前工作区允许的 + 本工作区 + 共享组）→ 只取 `active`（`review` 的带「待核对」标记、预算紧时最后考虑）→ 先用新鲜的素材（`memory_materials` 不 stale 的）→ 相关性（现在的三元组相似度，以后视效果加语义检索，纪要 §13.5）→ 按配额和预算装入。素材不够、或有 stale 的素材时，排一个「快照准备」记忆任务给下一次用；**这一次不等它**，用现有有效内容并在快照记录里标 `degraded`（纪要 §10.2、§13.2「不能无限阻塞」，见十二.9）。

### 6.3 注入点和防重复（已核对 Pi 1.4 接口）

- **注入**：保持现在的做法：任务开始时在 `before_agent_start` 里返回一条 `customType: "df-memory"`、`display: false` 的会话消息（写进会话文件，可审计、可解释「本次用了哪些记忆」）。
- **防重复堆积**：新增 `pi.on("context")`（每次调用模型前触发，可以改消息列表，类型 `ContextEvent`）：只保留**最后一条** `df-memory` 消息，更早的从发给模型的列表里去掉（会话文件里还在）。刷新快照时就不会越积越多（纪要 §10.5 第 1 条）。
- **纠正立即生效**：同一个 `context` 钩子里比对最后一条快照的 `item_versions` 和库里的当前版本：如果其中有条目被用户改了、撤销了、标了过时，就当场按新内容重组快照替换掉（纪要 §10.3「用户纠正需要及时生效」）。普通后台整理的结果不在这里换，等下一个任务（保持一次连续执行中稳定）。
- **刷新时机**（纪要 §10.3）：新会话的第一条消息；工作区切换；压缩之后；用户纠正 / 撤销；手动刷新；**任务边界**（协议见第十六节）。
- **防压缩后复活**（纪要 §10.5 第 3 条）：在 harness 的 `session_before_compact` 里（`CompactionPreparation.messagesToSummarize` 可以改）先把 `df-memory` 消息从要总结的消息里去掉，并在总结说明里加一句「不要把记忆快照里的内容写进摘要，它会单独重新提供」；压缩后下一条消息自动重新注入当前快照（现在的代码已经会，因为旧快照在压缩点之前）。另外总结完成后扫一遍摘要：如果出现了已失效条目的原文片段，记一条告警（测试里断言不出现）。
- **静默失败**（纪要 §10.5 第 7 条）：快照准备失败或降级时，快照记录 `failed`/`degraded`，窗口的上下文面板显示「本次记忆没有加载 / 部分加载」，提示词里加一行告诉主 Agent「记忆未能加载」，不拿不适用的旧快照充数。
- **按需检索**（纪要 §10.4）：`memory_search` 结果计入同一个预算的「补充」份额；超出时只返回最相关的几条和「还有 N 条」，不往上下文无限追加。

## 七、调度和成本（纪要 §13）

- 记忆任务队列 `memory_jobs`，优先级：用户的纠正 / 删除 / 恢复 > 当前任务的快照准备 > 任务结束后的提取 > 周期整理。
- 触发：任务结束（有新内容才排提取，按 `memory_extraction` 游标增量）；一级每周（周一凌晨或应用下次启动时补跑）；二级每周轻量 / 每月 / 每季；三级每月轻量 / 每季 / 每年；事件（纠正、冲突、工作区切换、压缩）。日历到期先程序检查有无变化，**没有变化不调模型**。
- 时钟：复用定时模块的调度器；测试用可注入的假时钟，模拟两周、一月、一季、一年（纪要 §16.1）。
- 成本：设置里「记忆后台预算」（每日 / 每月美元，独立于主任务，默认每日 $0.20，用户 2026-11-06 定）；用量记在 `usage_records`，来源 `memory`，仪表盘分开显示；主任务紧张、额度用完、预算到了 → 普通整理推迟（状态 `deferred`，显示在记忆页），不丢弃。
- 失败：最多重试 2 次（指数退避），再失败记 `failed` 和原因，留到下次周期。
- 「暂停整理」和「关闭记忆」分开：暂停整理时照常用有效快照；关闭记忆时不注入。

## 八、隔离覆盖整个调用链（纪要 §8）

每一处读记忆或历史的地方都过同一个范围函数 `allowedScopes(slot)`：快照组装、`memory_search`、`session_search`（会话索引按工作区过滤）、候选提取（只处理本会话所在工作区）、记忆 Agent 的输入、缓存和素材（`scope_key` 区分）。蝶君的会话范围是 `butterfly` 分区：读全局（被允许的）+ 蝶君分区，不读任何工作台工作区的私有记忆；反过来工作台也读不到蝶君分区。全局里「个人背景」类可以按工作区关掉（工作区设置）。跨工作区查找要用户临时授权，只对那一次有效，结果不自动保存。

## 九、遗忘、恢复、回撤（纪要 §11）

- 正常整理里的「自然遗忘」= 提炼后原条目 `archived`，保留关系和来源。
- 过时、冲突、被推翻：容量没满也要标，退出快照，保留记录。
- 三种「满了」分开：快照预算不足只减少加载；活跃容量满（见十二.4）先提炼合并，仍不够才由记忆 Agent 提**软遗忘方案**（候选顺序按纪要 §11.5，三级、锁定、已确认的重要决定排除），用户 review 后提交成一个批次；物理磁盘满暂停写入并提示。
- 恢复：单条恢复（从 `memory_versions`，必要时重新判断层级和范围）；整批回撤（`memory_ops` 的 batch，逐条比对版本，之后被用户改过的条目不覆盖，列出冲突让用户选）。
- 没有「回收站 30 天自动清空」。

## 十一、v0.2 记忆的迁移（纪要 §17）

- 时机：0.5 的数据库升级（v0.3.1 之后升级前会自动备份，可以回退）。
- `memories` 里 `active` 的条目 → `memory_items`：
  - `kind` 照搬（preference / background / experience）；`scope`、`cwd` → `scope`、`workspace_id`（新建 `workspaces` 记录）。
  - **层级**：都放二级，状态 `review`（标记「迁移，待复核」），**不因为旧就放三级**；记忆 Agent 第一次整理时逐条提出层级建议，用户批量确认。
  - `confidence`：v0.2 里用户确认过才会 `active` → `user_confirmed`；`source` 是用户明说的 → `user_explicit`。
  - 来源：`source_session` 有就写一条 `session` 来源；没有就**不补造**，只记 `migration`。
  - `replaced_by` → `supersedes` 关系；`candidate` 的条目照样是候选；`rejected` 的不迁。

- `memory_snapshots` 旧记录保留只读（界面「本次用了哪些记忆」还能看历史）。
- 旧表保留一个版本后删除。迁移有核对报告（条数、未迁移项及原因），可以回退到升级前的自动备份。

## 十三、测试（纪要 §16）

后台测试用假时钟和脚本化的假模型（现在的测试框架）：首次任务就有快照或明确降级；第 13 / 14 / 15 天边界；每周整理跳过无变化；提炼 / 直接进入 / 降级 / 失效都保留来源；推测和重复引用不变成证据；工作区隔离（快照、`memory_search`、`session_search`、提取、记忆 Agent 输入都测）；预算总和不超限；快照不重复堆积；被纠正的内容立即换掉；压缩后不复活（摘要里不出现失效条目）；软遗忘只在真正满额时、三级和锁定受保护；单条恢复和整批回撤不覆盖之后的用户修改；各模式的读写约束；中断不留半次更新；预算耗尽时排队不死循环。真实模型的效果观察（召回、干扰、重复解释次数、确认负担、延迟、token、成本）在 0.5 用一组人工标注样本对比 v0.2。

## 十四、0.5 的实现顺序（建议）

1. 新表 + 迁移 + 范围函数 + 操作接口（程序侧守门、事务、版本、留痕），先不接 Agent。
2. 快照组装改造：预算、配额、素材、`context` 钩子防重复和即时纠正、压缩防复活、降级显示。
3. 记忆 Agent 角色卡 + 任务队列 + 任务结束提取 + 每周整理。
4. 分层转化、冲突、二三级周期复查。
5. 软遗忘、恢复、回撤、彻底删除。
6. 界面：**0.5 只做最简的**——记忆日志（按天列出存了哪些、改了哪些、忘了哪些，能改、能删、能撤销；默认自动生效的安全网，第四节）、提升为全局的确认、「说记住了但没存」的提示和保存按钮（17.7）、设置项。完整的记忆页、「本次用了哪些记忆」「为什么没想起来」的界面在 0.11（后端优先，路线图第一节第 6 条）。

## 十五、v0.3.2 实测问题（2026-11-03，0.5 要逐条解决）

用户原话：「这个真得好好搞搞了，现在几乎整成不可用的状态了」。v0.3.3 只做了止血（见 [dev-guide.md](dev-guide.md) 第二节），0.5 的设计和验收要覆盖下面每一条：

1. **意思重复**：「回复要简练，少说话」和「回复要简练，别长篇大论；正常问答不要用 Showcard……」同一时刻从同一段对话进了记忆库。v0.3.3：写入前按字面相近度查重（`nearDuplicate`），更完整的变成「修改」建议；提取时把全部记忆给模型看。**字面不相近但意思相同的**（「希望用简体中文交流」和「思考和输出一律使用简体中文」）还拦不住 → 0.5 由记忆 Agent 做语义去重和合并（5.6）。
2. **身份混淆**：蝶君会话里提取出「用户叫蝶君，希望用简体中文交流」。原因：用户让 Agent 记住「我（Agent）叫蝶君」，存成了第一人称的「我是该平台的专属 Agent，名字叫蝶君」，又注入到每个会话的快照里；提取模型分不清「我」是谁。v0.3.3：提示词要求以「用户」为主语、Agent 的名字不是用户的信息。0.5：**关于 Agent 自己的设定**（名字、人设、对用户的称呼）单独成一类，不和用户的偏好、背景混在一起；工作台和蝶君分区（5.5）。
3. **来源看不清**：用户分不清哪条是自己批准的、哪条是 Agent 自己加的（「Agent 推断」其实是用户在待确认里点过接受的）。0.5 的记忆页（5.7）要显示「谁提出、谁确认、什么时候、从哪段对话来」，并能一键回到那段对话。
4. **候选太多、太碎**：每次运行后都提取，用户来不及看就点了接受。0.5：提取按任务结束和每周整理批量做（5.6），候选合并后再给用户看，支持批量确认和「这类以后不用问」。

## 十六、任务边界与快照刷新协议（2026-11-04，合并 Codex 报告 02）

来源：用户 2026-11-02 的《三级记忆：自然任务边界与快照刷新调研设计报告》（`…\DreamFlutter\档案馆\Codex\…Codex-02-…md`），用户的注释是「以自己的记忆系统为主体，重点研究自然任务边界刷新快照」。报告不替换本文的主体（三级、作用域、证据、保留与恢复），只把「什么时候换快照」细化成协议。下面是落到本项目的做法，和报告不同的地方单独标出。

### 16.1 五个时间尺度

消息、执行轮次（一次生成和它的工具交互）、任务（有明确目的和产出的工作单元）、会话（聊天容器）、目标（0.8 的 Goal，可以跨任务、跨会话）。**快照跟着「任务」换**，不跟消息、轮次走；同一会话可以先后有几个任务，同一任务的连续步骤（查日志 → 看代码 → 验证）不重建快照。

### 16.2 边界事件

每个会话在后台记一个「当前任务」（`memory_task_views`：任务 ID、会话、工作区 / 分区、开始原因、状态 进行中 / 挂起 / 结束、当前快照版本）。

| 事件 | 判定 | 做什么 |
|---|---|---|
| 新会话的第一条消息；定时任务的每次运行；写笺交给蝶君 | 确定边界 | 新任务，准备并启用新快照 |
| 切换工作区（含工作台 ↔ 蝶君分区） | 确定边界 | **先让旧范围的快照失效**，再准备新的；准备失败就无快照继续（标 `degraded`），绝不沿用旧工作区的 |
| 用户在界面点「作为新任务」，或明说「这件做完了，接下来……」 | 确定边界 | 旧任务结束（排一次提取），新任务新快照 |
| 新建目标、目标进入下一阶段（0.8） | 确定边界 | 共同约束保留，阶段相关记忆重选 |
| 同一会话里像是换了话题（隔 ≥ 2 小时，或消息较长且和当前任务相关度很低） | **候选边界** | 程序信号命中时才做一次轻量判断（辅助模型，一句话的分类，不是完整记忆 Agent 调用）；把握低就沿用当前任务。判为新任务时旧任务记「挂起」不记「完成」，消息下方出一个小提示「已按新任务处理 · 改为继续上一个」 |
| 跨天继续 | 候选边界 | 只检查快照素材有没有过期（stale），不按零点硬切 |
| 回复结束、命令退出、空闲、子 Agent 返回、读到新文件 | 普通活动 | 不触发 |
| 压缩完成 | 维护边界 | 核对快照版本是否还有效，按需重组；**不算任务结束** |

和报告的不同：报告没给具体信号，这里沿用原第十二节第 9 条的两个信号（时间间隔、相关度）作为触发轻量判断的门槛，避免每条消息都调模型。

### 16.3 两阶段刷新：准备和启用分开

```text
边界事件（带事件 ID，同一事件去重；短时间内的多个事件合并）
  → 排「快照准备」记忆任务，记下输入版本：用到的记忆条目版本、范围 / 权限版本、任务 ID
  → 记忆 Agent / 程序产出候选快照（后台）
  → 下一次调用模型前（Pi 的 context 钩子，6.3）检查：范围、版本有没有变、预算
       版本变了 → 丢弃或只重做受影响的部分（比较后提交，不是「最后完成的赢」）
  → 启用一个确定的版本，写「已采用」记录
```

- 只在**安全边界**换：下一次请求构建前，或一组工具调用和结果完整结束后；模型生成到一半时不改它的上下文，不拆开 tool-call 和 tool-result。
- 一个任务只有一个生效快照（6.3 的防重复已经保证发给模型的只有最后一条）。
- 准备没完成就到点了：不等（第十二节第 9 条），用现有有效素材，标 `degraded`。

### 16.4 紧急纠正不等边界

用户的纠正、删除、撤销共享、收紧权限：

1. 立即让受影响的条目和由它组出来的快照失效（6.3 的「纠正立即生效」已有，扩到删除、撤销共享和权限）；
2. 正在运行时，纠正作为插话（steer）送给主 Agent；
3. 下一次工具调用或模型请求前检查最新权限，不等任务结束；
4. 压缩摘要里引用了被推翻内容的，标记失效（6.3 的「防压缩后复活」，0.5 的上下文服务一起做）。

已经发出去的外部请求收不回，界面如实说明，不把「刷新快照」说成撤销。

### 16.5 两张回执

「已保存」和「当前任务已用上」分开显示：

- 用户说「记住…」：事务提交成功才显示「已保存到〈分区〉/〈层级〉」；待确认的候选显示「已提出，等你确认」，不能显示成已记住；
- 当前任务是否已经采用新内容另写一行（「当前任务已采用」或「下个任务开始使用」）；
- 后台整理没有重要变化时不弹提示，记忆页里集中看。

### 16.6 模式

在第十节的表上加一个会话级的「只读记忆」：读快照，不写不提取，检测到边界也不偷偷生成正式条目。无痕模式下边界检测、快照准备、索引、后台记忆任务一律不跑。

### 16.7 和目标、压缩的分工

任务边界是整理的机会，不是晋升或删除的命令；任务结束可以提一个有证据的经验候选，不直接变成全局永久记忆。**是否继续执行只由 0.8 的调度者决定**：记忆任务完成只发「候选就绪」，压缩完成只发「上下文可用」，都不自己唤醒会话。

### 16.8 加到第十三节的测试

同一会话换话题（旧任务挂起、新快照不混入别的工作区）；连续调试多轮快照不重建；跨天继续不误判完成；准备期间用户纠正（旧候选不能提交）；收回权限后下一次受保护操作前生效；保存失败不出「已记住」；压缩后被否定的事实不复活；无痕 / 只读下后台队列也不跑；同一边界事件重复到达只准备一次；成本对照：每条消息刷新、只在会话开始刷新、本协议三种的相关性、延迟和花费。

## 十七、遗忘机制补强（2026-11-06，用户已定稿）

来源：v0.4.0 测试报告第 10 条（遗忘机制是平台的独特能力，开发前要强化完整设计）和 Hermes 的调研 [research/hermes-memory.md](research/hermes-memory.md)。

**不改的部分**：纪要 §11 用户已经定的原则全部保留：三级一般不遗忘；遗忘主要发生在升级和提炼中（自然遗忘）；只有活跃容量真正耗尽才考虑主动软遗忘，要留痕、可 review、可恢复、可回撤；「长期没被用」只是复核线索，「被反复展示」也不增加保留价值；彻底删除是用户的单独意图。第九节和第十二节第 4–8 条照旧。

**补的部分**：原设计把遗忘看成「满了以后怎么腾地方」，其实记忆出问题更多是另外两种情况：**该忘的忘不掉**（过时的、错的、有害的内容一直留在快照里，Hermes 称为「固化成拒绝做事的理由」），和**不该忘的被意外忘掉**（压缩、提取遗漏、说记住了其实没存）。下面按「一条记忆的一生」把遗忘补全。

### 17.1 遗忘的全部路径

| 路径 | 什么时候 | 结果 | 谁决定 |
|---|---|---|---|
| 0. 不记 | 写入之前 | 不进记忆库（17.2） | 程序规则 + 记忆 Agent |
| 1. 自然遗忘 | 升级、提炼时 | 原条目 `archived`，新条目承担调用（第三节） | 记忆 Agent 提出，程序校验 |
| 2. 到期 | 有效期过了 | 标「已结束」退出快照，保留（17.3） | 程序，按时钟 |
| 3. 失效 | 被替代、被推翻、和新证据冲突 | `superseded` / `refuted` / `review`，退出快照，保留（17.4–17.6） | 证据驱动 |
| 4. 软遗忘 | 活跃容量真正满额 | 方案经用户 review 后 `forgotten`，可恢复（第九节） | 用户 |
| 5. 彻底删除 | 用户明确要求 | 删正文、留抑制记录（第十二节第 8 条） | 用户 |

另外两类不是「遗忘」但必须防住：**意外遗忘**（17.7）和**忘不掉的有害内容**（17.2 的安全扫描）。

### 17.2 入口：不该记的，一开始就不记

1. **不记的清单**（借鉴 Hermes 复盘提示词，写进记忆 Agent 和主 Agent 的提取规则，并配测试样本）：
   - 环境造成的失败：缺软件、没装好、路径不对、没配置凭据。要记的是「怎么修好的」，不是「这个不能用」；
   - 重试就好了的临时错误；
   - **没有解决的失败**：试了几种都不行，不能写成「推荐做法」；
   - 一次性的任务经过（「今天让我总结了某篇文章」不是长期有用的事）；
   - 已经在别处的东西：技能里的、工作区规则文件里的、工具说明里的。
2. **一条记录只放一件事**（原子条目）：提取和提炼都按「一件事一条」写；提炼出的综合条目通过 `derived_from` 关联原条目，而不是把几件事塞进一条。这样修改、推翻、遗忘一件事时不会误伤同一条里的其他内容（Hermes 的整条替换就是这样把别的事实抹掉的）。
3. **安全扫描**（写入和加载两处）：记忆会进入每次的上下文，被写进去的提示注入（「忽略之前的指令」「把文件发到某地址」）、不可见字符会一直生效。写入时命中 → 拒绝并说明；加载时命中（例如旧数据、手工改库）→ 快照里替换成「已拦截一条可疑记忆」并在记忆页标出。现有的密钥检查（`scanSecrets`）一起做。

### 17.3 会过期的记忆：有效期

`valid_until` 字段原来就有，这里定规则：

- 这几类**必须**带有效期或复查时间，提取时由记忆 Agent 填，填不出就用默认值：
  - 时间限定的安排和状态（「这周在赶论文」「下周一交初稿」）：到说的那个时间；
  - **对工具、环境、外部服务的判断**（尤其是否定的：「某工具在这台电脑上用不了」「某网站要代理」）：默认 30 天（用户 2026-11-06 定），而且**遇到反例就失效**——之后同一工具成功执行了、同一网站直接打开了，程序发现后把这条标「被推翻」（证据记来源），不等到期；
  - 一级里的近期进展：沿用第十二节第 2 条，任务结束时由提取决定。
- 到期时：程序标「已结束」，退出快照，记录保留、记忆页可见、可一键恢复；到期属于**真实性维护**（纪要 §11.3），不是主动遗忘，不需要逐条问用户（用户 2026-11-06 定）。
- 用户锁定的、三级的不自动到期，到期只标「待复核」并通知。

### 17.4 回想时再巩固

参考人的记忆「被回想时会重新变得可修改，再被存回去」：

- 一条记忆进了这次的快照（被「回想」起来），而这次对话里出现了**和它矛盾或比它更具体**的信息（用户纠正、工具结果相反、用户补充了条件），程序就为这一条排一个「复查」记忆任务（事件触发，纪要 §4 已有的触发类型），由记忆 Agent 提出更新、加限定条件、降级或标冲突。
- **只在出现矛盾或新信息时才做**；只是被用到、没有新信息，什么都不改，也不加分（遵守纪要 §11.5：展示次数不增加保留价值）。
- 判断「有没有矛盾」先用程序的预筛（17.6），命中才调模型，控制成本。

### 17.5 证据的分量：负面比正面重

- 用户纠正、被推翻、工具结果相反：一次就足以让条目退出快照、进入复查。
- 「又被确认了一次」：只有来自**新的、独立的来源**（不同会话、用户本人、工具或任务结果）才算；助手自己复述、快照里被展示都不算（第二节 `memory_sources` 已规定）。
- 这和 Hermes 可信度的「有用 +0.05、没用 −0.10」是同一个方向，但我们不用一个分数，而是用来源和状态表达，可解释、可追溯。

### 17.6 矛盾预筛（程序，不调模型）

新条目写入、或一条记忆被回想时：找出作用域相同、**说的是同一对象（实体、属性重合度高）但内容差异大**的已有条目，列为「可能冲突」交给记忆 Agent 判断（借鉴 Hermes holographic 插件的做法）。否定句和数字、日期不同要特别加权（「用中文回复」和「不要用中文回复」字面很像，意思相反）。

### 17.7 防止意外遗忘

1. **压缩不能让提取漏掉内容**：压缩前检查记忆提取的游标是否已经覆盖了要被总结的那一段；没覆盖就先排提取（我们的压缩不删会话文件里的原文，所以只需保证游标不跳过；不需要像 Hermes 那样提取失败就不压缩）。压缩摘要不把失效条目带回来（6.3 已有）。
2. **「说记住了但没存」**：主 Agent 的回复里有「记住了 / 已保存到记忆」这类说法，但这一轮没有任何记忆操作成功 → 程序在回复下方标出「这条没有真正保存」，给一个「保存」按钮（16.5 两张回执的补充）。
3. **会话被删除时**：从它提取的记忆怎么办，见 17.10 第 5 条。
4. **关于 Agent 自己的设定和用户信息分开**（第十五节第 2 条），防止「用户叫蝶君」这类错误把真正的用户信息挤掉或覆盖。

### 17.8 「为什么没想起来」能查

每条记忆在记忆页（以及「本次用了哪些记忆」）里都能看到它这次**为什么没进快照**：预算不够、和这次任务不相关、已结束（到期）、被替代 / 被推翻、在复查中、软遗忘了、不在这次允许的作用域里。用户能据此恢复、改有效期、锁定或纠正。界面 → 0.11；数据和接口在 0.5 做。

### 17.9 留给技能（0.7）的借鉴

Hermes 的技能管理员适合技能，不适合记忆，记在这里给 0.7 用：区分技能归属（用户的、Agent 自建的、内置的、市场装的，只有 Agent 自建的会被自动整理）；陈旧和归档（从不自动删除）；钉住；被定时任务引用的不动；每次整理前快照；每次改动一条审计记录、可单独撤销；清理只能用户明确执行。

### 17.10 用户的答复（2026-11-06）

1. 有效期到了自动标「已结束」、退出快照、不逐条问（记忆页能看、能恢复）：**同意**。
2. 对工具、环境的判断默认有效期 **30 天**，遇到反例自动推翻：**同意**。
3. 回想时发现矛盾自动排一次复查（用记忆的后台预算）：**同意**。
4. 「说记住了但没存」在回复下方提示并给「保存」按钮：**同意**。
5. 删除会话时，从它提取出的记忆**保留**，来源标「会话已删除」。
6. 原本设想里没有这一节没写到的部分（「暂时没了」）。

同时用户提出：**记忆默认自动生效、不逐条审批**，在界面里按天看存了哪些、忘了哪些，可以直接修改、删除。见第四节开头。

### 17.11 加到第十三节的测试

不记的清单（每类各一个样本，提取后不该出现在记忆库）；一条多事实的旧条目被修改时其他内容不丢（迁移来的旧条目也测）；注入样本写入被拒、加载被拦；时间限定的安排到期退出快照、可恢复；「某工具用不了」在该工具成功执行后被推翻；回想时出现矛盾才排复查、没有矛盾不排；展示次数增加不改变任何状态；否定句的冲突预筛命中；压缩前游标没覆盖时先排提取；「说记住了但没存」被标出；锁定和三级不自动到期。
