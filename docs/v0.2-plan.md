## 二、工作内容

标记：**必做** / **可选**（必做完成后按价值挑）。

### A. 体验与界面重设计（最优先）

先定方案，再动代码。

1. **调研**：HanaAgent（openhanako）的布局和交互；同类桌面 Agent 客户端的信息架构；世界名画和艺术品中的蝴蝶意象（作为视觉参考）。
2. **信息架构和布局方案**：导航怎么分、每页的主次、常用操作放哪里、新用户第一次打开看到什么。
3. **三套视觉方向的设计稿**：都基于「文艺、简洁、大气、蝴蝶元素、世界名画主题」，各取一幅或一类作品作为主题来源，做成可以直接点看的页面（对话页、书桌、仪表盘三屏）。你选一套（或混搭）后再落地。
4. **设计系统落地**：颜色、字体、间距、圆角、阴影、图标、插图、动效统一收在 `theme.dart`，每套主题可切换。
5. **阅读与反馈体验（必做）**：
   - 正文排版：舒适的行宽、行高、段距；代码高亮；表格、引用、数学公式。
   - 思考过程：默认折叠成一行「思考了 12 秒」，展开后弱化显示。
   - 工具调用：按类型呈现。命令显示成终端样式（命令 + 输出）；改文件显示差异对比；读取、搜索显示成紧凑的一行；连续多个工具调用合并成一组。
   - 动效：消息出现、流式输出的光标、工具运行中的状态、面板展开和收起，都要平滑但克制。
   - 界面缩放：Ctrl + 加号 / 减号 / 0，也放进外观设置；文字大小的入口放到明显的位置。
6. **上手引导（必做）**：第一次打开时的引导（连接模型、选工作区、试一个任务），各页面的空状态写清楚能做什么。

### B. 对话体验（必做）

1. **AI 回复上的操作**：复制（整条 / 代码块 / Markdown 原文）、重新生成（可以换模型）、版本切换 `‹ 1/3 ›`、从这里分叉。鼠标移上去时出现，键盘也能操作。
2. **每条消息的数据**：模型、输入 / 输出 / 缓存 token、首字延迟、生成速度（token/秒）、耗时、花费、时间。默认显示一行小字，可以展开。
3. **分支树面板**：一个会话里所有版本和分支的树状图，点击跳转（后台已支持树导航，只差界面）。
4. **输入框增强**：拖放和粘贴文件，@ 引用书桌资料，/ 命令补全，插话和排队提示更清楚。

### C. 多模态

1. **修复图片输入（必做）**：查清图片在哪一步丢了（窗口 → 后台 → Pi → 模型接口），加端到端测试。
2. **不支持图片的模型（必做）**：发图时自动用一个支持视觉的辅助模型先「看图转述」，再交给当前模型；界面上说明这样做了。
3. **文件输入（必做）**：PDF、Word、表格、文本拖进对话，自动转成文字或交给 Agent 用工具读取。
4. **富内容输出（必做）**：对话里直接渲染 Mermaid 图、图表（Agent 输出数据，界面画）、SVG、HTML 演示（在隔离的预览窗口里运行），可以放大、复制、另存。
5. 图片生成（可选）：接图片生成模型，结果显示在对话里并存进产物。

### D. 统一模型网关与仪表盘（必做）

**调研结论**（2026-10-29 在 GitHub 上查看）：

| 项目 | 是什么 | 适合我们的地方 | 不适合的地方 |
|---|---|---|---|
| [New API](https://github.com/QuantumNous/new-api)（约 5.1 万星，AGPL-3.0，Go） | 自托管的 AI 网关：渠道、优先级和权重、多 Key、重试、模型映射、配额、按用量计价、用量日志、OpenAI / Claude / Gemini 协议互转 | 渠道 + 优先级 + 权重 + 多 Key + 计价，这套模型很成熟 | 面向多用户和团队，要单独跑服务（Docker 或二进制），概念比个人使用重很多 |
| [CC Switch](https://github.com/farion1231/cc-switch)（约 15 万星，MIT，Tauri） | 桌面端，给 Claude Code、Codex、Pi 等一键切换服务商；本地路由、协议转换、故障自动切换（熔断 + 健康检查）、聚合模式、用量统计、90+ 预置服务商 | 个人桌面场景，和你现有习惯一致（你的 DeepSeek 就是通过它配的）；「故障队列 + 熔断」「整流器（不支持图片时降级等）」值得借鉴 | 它管的是外部命令行工具，不是我们这个 App 的会话 |
| LiteLLM（Python，MIT） | 代理网关：虚拟 Key、预算、备用链、花费统计 | 预算和花费统计的做法 | 要带一个 Python 运行环境，对桌面应用太重（本次没有重新查看它的页面） |

**建议：在后台里自建一个轻量的个人网关**，概念借鉴 New API（渠道、优先级、权重、多 Key、计价），故障切换借鉴 CC Switch（故障队列、熔断、健康检查、整流）。理由：

- 单用户桌面应用不需要多用户、分组、权限这一层；
- 不必再多跑一个服务或装 Docker；
- 我们已有 Pi 的服务商层、用量数据库和备用模型链，往上加最省事；
- 同时支持**导入** CC Switch 和 Pi 现有的配置；已经在用 New API 的话，也可以把它当成一个渠道接进来。

**功能**：

1. **渠道**：每个渠道 = 一个接口地址 + 一个或多个 Key + 可用的模型 + 价格；支持 OpenAI / Anthropic / Gemini 兼容接口，以及常见平台的 Token Plan（编程套餐）。
2. **模型路由**：一个「逻辑模型」（例如「主力对话」「便宜快速」「看图」）背后挂多个渠道，按优先级、权重选择；限流、出错、额度用完时自动换下一个，带熔断和恢复探测。
3. **额度与余额**：Token Plan 的周期额度（如 5 小时 / 每周）跟踪和提醒；支持余额接口的平台自动查询余额。
4. **仪表盘**：今日 / 本周 / 本月花费和 token；按渠道、Key、模型、任务、工作区拆分；趋势图；每个渠道的健康状态和最近错误；预算和提醒。
5. **服务商页改造**：删掉内置预置服务商列表，改成「渠道管理」；Key 继续用 Windows 账户加密保存。
6. 对外提供本地接口（可选）：让 Claude Code、Codex 等其他工具也走这个网关，统一记账。

### G. Agent 模式（新增，阶段 3a，先于网关）

调研报告：[research/deepseek-harness.md](research/deepseek-harness.md)（Codex 只读调研，dsh 提交 `ce7073d`，MIT 许可）。

- **做法**：**不**把 DeepSeek Harness 的运行时接进来，也不随应用带它；按它的设计思路**在我们现有的 Pi 后台里复现**。所有会话仍然跑在 Pi 上，旧会话照常打开，不另设「旧 Pi 模式」。
- **两种模式**（会话级设置，新会话默认「标准」）：
  - **标准**：按 dsh 标准预设的组成复现：提示词结构（身份 → 计划规则 → 各工具说明 → 宿主提示）、工具集与参数和描述原文（`read`/`write`/`edit`/`glob`/`grep`/shell/`read_image`/`todo_write`/计划模式等，按需取舍后列清单）、动态内容（工作区指令、技能目录、时间）放进历史而不是改 system 前缀、工具结果裁剪（达到压缩阈值时先裁：超过 8192 字符保留头 4096 + 尾 1024）、dsh 的压缩参数和重试策略。**再加上我们的记忆和技能工具**（用户确认：标准保留附加功能）。
  - **极简**：按 **dsh 当前官方 minimal**：系统提示词只有 `You are a helpful software engineer assistant.`，工具只有持久 PowerShell（Windows）/ 持久 bash、`read_image`、`working_directory`，保留必需的工作目录快照和自动压缩；**不加**记忆注入、记忆工具、技能、书桌附件提示（后台照常提取候选记忆）。不采用早期训练版（shell + `str_replace_editor`、不压缩）。
- **两种模式共用的 DeepSeek 传输修正**：思考内容（reasoning_content）在带工具的请求里完整回传（Pi 1.4.0 已基本支持，补回归测试锁住）；缓存友好的请求顺序；dsh 的空回复 / 限流 / 超时重试规则。
- **审批**：两种模式都沿用我们现有的审批（按操作类型；持久 shell 和编辑按命令动作分类），没有改成 dsh 的沙箱。
- **已知要处理**：`core.ts` 开会话时调 `setAutoCompactionEnabled()` 会写用户的全局 Pi 设置，改成会话内隔离的设置；书桌没有注册 `desk_*` 工具（审批白名单里的名字是空的）。
- **Pi 做不到完全一致的地方**（实现时按 dsh 思路尽量贴近，并在文档里标明差异）：达到 `max_tokens` 时的停止语义、工具结果裁剪的持久化替换、压缩的完整时序。
- **验证**：faux 假模型测试锁住两种模式的提示词和工具清单快照、思考回传、裁剪阈值；再用真实 DeepSeek 跑一组小任务对比「改造前 / 标准 / 极简」（成功率、400 和重试次数、token、缓存命中、花费）。
- 后端实现交给 Codex（经 Agent Bridge 后台任务），Claude 负责方案、审查和界面。

### H. Showcard 交互卡片（阶段 4，与富内容输出一起做）

调研报告：[research/showcard.md](research/showcard.md)（规范 1.0，[liliMozi/showcard](https://github.com/liliMozi/showcard)，代码 MIT、规范 CC BY 4.0；OpenHanako 是同源宿主）。

- **完整接入**：Agent 用 `show_card` 类工具在对话里生成卡片；卡片状态持久化（每张卡 64 KiB）；`toolBindings` 工具调用 + 按「主机名 / 程序 / 工具 / 目录」授权，三档记忆（只这一次 / 本会话 / 始终）且可撤销；导出 `.card.html` / `.card.zip`、导入别人的卡片（信任归零）；卡片可以收进书桌。C4 里的「HTML 演示」就用 Showcard 卡片实现。
- **显示**：内嵌在对话里，**最新的一张和点过的一张是活的**（WebView2），其余显示为截图，点一下激活；可放大到右栏或单独窗口。卡片由 Node 后台的本地 HTTP 服务按实例签发 CSP 提供，窗口里用宿主外壳页 + iframe 加载（不能用 srcdoc / 字符串加载）。
- 极简模式不提供卡片工具（与「极简不加附加功能」一致）。
