## 一、怎么排的

1. **不按测试记录的顺序**，按依赖关系排（用户明确要求）：先打地基，再统一外壳，之后的新功能都做在新外壳上；后面的版本依赖前面的成果。
   - 安全、数据目录、沙箱要一起设计 → 同在 0.3。
   - 外壳改动牵涉每个页面 → 0.4 先做，避免后面的新页面返工。
   - 长任务的后台机制（0.7）→ 记忆 Agent（0.8）→ 书桌的常驻 Agent（0.9）。
2. **用户已经定下的**：Docker 沙箱在 0.3；三级记忆在 0.3、0.4 讨论设计，之后实现；0.9 做一次和 v0.2 一样的深度测试，然后发布 1.0；「大肥鱼」类 Agent 留到以后。
3. **主题**按小版本（x.x.1）陆续加，不占主版本的工作量（33）。
4. **尽量均匀**（用户要求「合理均匀」）：外壳改动最多，0.4 只放框架、右侧面板和对话呈现；弹窗 / 页面统一和设置重排放到 0.5，提问框放到 0.7，和插话、清单这些「运行中的互动」一起做。

## 三、每个版本的通用流程

1. **调研**（需要的话）：广泛调研交给 Antigravity（经 Agent Bridge，后台任务），报告放 `docs/research/`，AI 给的内容一律当待核验素材。
2. **设计确认**：需要用户定的事（列在每个版本的「要用户定的」里）在开工前一次问清；界面设计先出设计稿让用户挑（像 v0.2 的「蛱蝶」那样）。
3. **实现**：Claude 写代码（前后端都写）；每个改动配单元测试 / 组件测试；后台 `core/test/`，窗口 `app/test/`。
4. **测试**：后台、窗口、协议层全量；视觉检查截图（`integration_test/look_test.dart`）；真实模型 E2E **走用户在应用里配好的 OpenCode Go 渠道**（`deepseek-v4.1-flash`，E2E 用 `core/scripts/copy-channels.ts` 复制渠道，**不要在测试里新建渠道**）。
5. **审查**：Codex 只做必要的只读审查（额度少），只审这个版本的高风险部分。
6. **发布**：用户验收 → 本地打 tag（不推送）→ 更新 `docs/HANDOFF.md`、发布说明、这份计划的状态。

## 五、各版本详细计划

### v0.3　地基与安全

**目标**：Agent 执行命令和代码可以放进隔离环境；安全设置成体系；用户能看到、能改每类数据放在哪；应用能自己检查和安装更新；三级记忆有完整的设计文档。

**工作项**

- **3.1 安全调研**（Antigravity，开工第一件）（10）：成熟 Agent 产品（Claude Code、Codex、Cursor、OpenHands、Goose、Cline 等）的权限模型、沙箱、提示注入防护、密钥管理、操作审计、网络出站控制；输出「我们缺什么、建议做什么」清单。
- **3.2 Docker 沙箱**（14）。原文：「把这个软件给隔离开来进行运行，这样更方便管理优化」。Flutter 窗口本身不能进容器，有两个方案，**开工前请用户选**：
  - **方案 A：整个后台进容器**（更接近原文）。Node 后台（Pi、所有会话、工具、数据库）跑在容器里，窗口在本机经 127.0.0.1 端口连它。
    - 好处：整个 Agent 和本机完全隔开，环境一致、好管理、好迁移。
    - 代价：工作区要挂载进容器才能读写；Windows 路径和容器路径要换算；Key 现在用 Windows DPAPI 加密，容器里用不了，要换一种加密方式；Word / Excel 自动化（COM）这类只能在 Windows 本机跑的任务做不了（需要一个本机执行通道）。
  - **方案 B：只隔离执行环境**。后台仍在本机，Agent 的 `pwsh` / `bash` 命令和代码在容器里执行（工作区挂载进去）；每个工作区可选「本机运行 / 沙箱运行」。
    - 好处：改动小，Word 自动化等本机任务照常。
    - 代价：隔离得没那么彻底。
  - 两个方案都要：没装 Docker Desktop 时，设置里给出安装指引，其余功能照常；容器的网络默认能出网，可以关；先做技术验证（Pi 的工具调用换执行环境是否方便）。
- **3.3 安全设置扩充**（10）：根据 3.1 的结论扩充「设置 › 安全与审批」。候选：命令黑名单 / 白名单、敏感路径保护（不许读写的目录）、网络访问控制、密钥扫描（提交给模型前遮住看起来像 Key 的内容）、操作审计日志（谁在什么时候执行了什么，能查、能导出）、外部内容（网页、文件）里的指令提示注入提醒。具体做哪些等 3.1 出来后和用户一起定。
- **3.4 数据目录分层**（12）
  - 「设置 › 数据与存储」列出每类数据：会话记录、后台数据库、记忆、技能、任务模板、卡片、产物、日志、加密密钥。每类显示位置、大小，可以打开文件夹。
  - 原文要求各类文件**都要**能看、能改位置：原则上每类都能改，改的时候搬运已有数据；会话、技能、模板目录 Pi CLI 也要读，改位置时同步 Pi 的配置；确实不能改的写明原因。
  - 默认位置按「应用数据 / 用户内容 / 缓存」分层整理。
- **3.5 版本与更新**（13）。原文：「版本管理更新**还有其他的东西**你也多调研完善一下」（截图是「设置 › 关于」）。先调研成熟桌面应用的关于页和更新机制（Antigravity），再把「关于」做成完整的版本页：
  - 显示应用、后台、Pi 的版本，检查更新，更新日志；
  - 其他候选（看调研）：问题反馈、导出诊断信息（日志打包，Key 打码）、许可证和第三方声明、数据备份与恢复；
  - 发布包（安装包）的打包方式；更新前自动备份数据库，数据库迁移失败可回滚；
  - 开机启动、关窗口时的行为（不是测试记录里的，是 v0.2 设计稿里有、没做的两项）。
  - 发布渠道（GitHub Releases 或其他）要用户定。
- **3.6 三级记忆设计文档**（25，只出设计不实现；如果用户原意是 0.3–0.4 就做出来，见第二节）：调研（Antigravity：MemGPT / Letta、mem0、Zep、Claude / ChatGPT 的记忆、OpenHanako 的记忆快照等）+ 设计文档 `docs/memory-design.md`。文档内容和讨论点见 v0.8。0.3 出初稿，0.4 期间和用户讨论定稿。

**依赖**：无（地基）。
**要用户定的**：沙箱方案 A 还是 B；能否接受安装 Docker Desktop（WSL2）；沙箱默认开还是关；更新包从哪里发布；安全设置做哪些（看 3.1 的清单）。
**验收**：按选定的方案，Agent 的命令确实在容器里运行（有自动测试，没装 Docker 时跳过），关掉沙箱后照常在本机运行；数据页列出的位置都正确，改位置后数据可用；检查更新能走通（可以用测试源）；记忆设计文档初稿交给用户。
**风险**：Docker 在 Windows 上的体积和启动速度；容器里路径和本机路径的换算；Pi 的工具调用接口是否方便换执行环境（先做技术验证）。

### v0.4　外壳与对话

**目标**：把「刷了漆的毛坯房」（28）变成统一设计的应用：品牌、窗口框架、左右栏、对话过程的呈现。

**工作项**

- **4.2 窗口框架**（35、29）：参考 Claude 桌面版：
  - 顶栏和页面标题合成一层（v0.2 的自绘顶栏是简版）；
  - 左侧栏重新设计：导航、会话列表、工作区切换的布局和交互。现在「对话」标题旁边挤着工作区小标签，布局奇怪；
  - 用户给的参考是 Claude 桌面版的侧栏：顶部是「新建、搜索」等固定入口，下面按项目（对应我们的工作区）分组列出会话，每组可以折叠、组上有新建和筛选按钮，用户信息和设置在底部；
  - 「对话右边进行工作区操作」（现在切换工作区的小标签在对话标题旁边）改成 Claude 那种做法：工作区就是侧栏里的分组。
- **4.3 右侧工作区面板**（18、27）
  - 现在的右栏「本次运行」只是一长串步骤，用户说「都是无效信息、太繁杂」。改成分块：
    - 进度（计划清单）；
    - 改动的文件；
    - 产物与预览；
    - 后台任务；
    - 上下文与花费；
    - 本次用到的记忆和技能。
  - 参考 Codex 和 Claude 的面板设计。
  - 右上角「⋯」菜单里的功能放到显眼位置：存成技能、存为模板、定时接着做、查看用到的记忆、刷新记忆快照。
- **4.4 对话过程的呈现**（32）
  - 思考默认折叠，折叠时一行写「在干什么」；
  - 运行命令的终端块颜色和背景统一，不再突兀，默认折叠；
  - 看图、搜索、读网页、调用 MCP 等工具各占一行、可展开看详情（这些比思维链重要）；
  - 看过的图片可以点开预览；
  - 用户说好看的现有样式（写入文件的差异块、修改块）保留。
- **4.5 回复下方的信息**（21）：用户对 Word 文档多轮任务的输出质量和观感满意，只是下面那行「模型 · token · 耗时」有点乱、有点大，操作按钮太小。改成：信息行精简，和操作按钮一起平时隐藏、鼠标移上去才显示；按钮加大。
- **4.6 输入框里的模式选择**（6、9）
  - 模式选择放到开始对话的地方（输入框），设置里只留默认值；
  - 加第三种「**无痕模式**」，原文：「不使用记忆也不计入记忆的极简模式，相当于完全纯净的 pi agent harness，做一些测试、临时问答、完全客观不掺杂其他东西的任务」。做法：极简模式的工具和提示词 + 不读记忆 + 不提取候选记忆（现在的极简模式会在后台照常提取候选记忆）；
  - 现有的「临时对话」（会话栏的眼睛按钮）不保存会话记录，和无痕模式不是一回事。无痕模式要不要保存记录、两者要不要合并，请用户定。

**依赖**：无硬依赖，但要在 0.5–0.9 之前完成。
**要用户定的**：品牌讨论（4.1）；从 2–3 套框架设计稿里挑一套（4.2–4.3）；无痕模式和临时对话的关系（4.6）。
**验收**：设计稿用户确认；视觉检查截图覆盖所有页面的浅色 / 深色；E2E 按新界面更新并通过。
**风险**：仍是改动最多的一版；其余页面跟着新框架的调整可以放到 0.4.x。

### v0.7　长任务

**目标**：长任务能放到后台、能插话、进度清楚可见，每一步中间结果用户都看得到；运行中的提问、插话、清单做成一套。

**工作项**

- **7.1 后台任务与等待**（22）：参考 Claude Code 的后台任务：
  - 长的子任务和脚本放到后台，主流程继续；
  - 主流程也可以主动停下来，等后台任务完成拿到结果再继续（触发机制：任务完成 → 通知 Agent → 继续）；
  - 在 v0.2 已有的 `pwsh` 后台任务基础上扩展：后台子 Agent、等待工具、窗口里的后台任务列表（显示在 0.4 的右侧面板）。
- **7.2 插话**（23）：默认仍是「这一步做完就插进去」（排队），加一个「**立即插入**」按钮：打断当前步骤，马上把消息交给 Agent。
  - 用户截图里排队的那条是「？怎么停下来了」，说明当时 Agent 看起来停住了、用户在等。开工时顺带查一下长命令运行时界面有没有给出足够的进度反馈。
- **7.3 计划清单**（23）：Agent 列的计划**在对话框上**显示，一项项完成打勾。理解成固定在输入框上方、随时可见（像 Claude、Codex 那样），现在只在右栏。参考成熟 Agent 的做法（调研）。
- **7.4 中间过程可见**（17）：
  - Agent 渲染 HTML、画图表、看截图时，每一步的图片都显示在对话里，用户能及时纠错；
  - 大数据用 Python 处理；在用户提示下用 MATLAB（检测本机 MATLAB，经命令行调用）；
  - 文档处理（Word / Excel / PDF）、表格数据绘图和可视化输出的能力补齐。
- **7.5 提问框设计**（15）：用户觉得 Agent 主动提问「很高效、及时强制反馈、解决问题」，但界面是毛坯。按 0.4 的新设计重做（选项卡片、自己回答、跳过），和插话、清单一起做成一套「运行中的互动」。
- **7.6 长任务测试集**：用户在测试记录里提到的场景做成可重复的测试任务：文档处理、表格可视化、Python 大数据、MATLAB、HTML 渲染。用 OpenCode Go 跑，记录成功率、轮数、花费。

**依赖**：0.4（右侧面板、对话呈现），0.3（沙箱里跑 Python）。
**要用户定的**：本机 MATLAB 的版本和路径；立即插入的确认方式（直接打断还是先问）。
**验收**：
- 一个需要 5 分钟以上脚本的任务：Agent 放到后台，期间能对话，脚本结束后自动继续；
- 「立即插入」能打断正在跑的命令；
- 清单在对话里逐项打勾；
- 测试集全部跑完并留下报告。

### v0.8　记忆系统

**目标**：按 0.3 / 0.4 定稿的设计实现三级记忆和专门管理记忆的 Agent。（如果用户原意是 0.3–0.4 就做出来，这一版的内容提前，见第二节。）

原文要点：「记忆快照的机制还是不错的，但是还可以根据我们的平台和需求做进一步的优化，在它的基础上……这里也是我们下一个版本的设计重点」。

**工作项**（以设计文档为准，下面是要在设计里回答的问题）

- **8.1 三级记忆**（25）：短期记忆、月度 / 季度记忆、年度 / 长期 / 永久记忆。
  - 三者的占比；
  - 各级之间怎么转化（短期 → 月度的提炼时机，月度 → 长期的标准）；
  - 每级的记录方式（原文 / 摘要 / 结构化）。
- **8.2 上下文预算**：记忆在上下文窗口里的占比要合适，不能影响工作质量、不能过度增加花费；阈值可设（和 5.3 的上下文设置联动）。
- **8.3 遗忘**：记忆过多时主动遗忘和删除（按时间、使用频率、重要度），删除前可确认，可恢复。
- **8.4 通用记忆和工作区记忆**：隔离与互通的规则（现在已有全局 / 工作区两种范围，要扩展）。
- **8.5 记忆 Agent**：一个专门管理记忆的后台 Agent，负责提炼、转化、遗忘、去重，用 0.7 的后台机制运行。
- **8.6 记忆强度和频率**（9）：设置里可选记忆的详细程度（越详细越丰富）和写入频率（每次任务后 / 每天 / 手动）。
- **8.7 迁移**：v0.2 的记忆库、常驻记忆块、待确认候选迁移到新体系；现有的记忆快照机制（用户觉得不错）保留并扩展。

**依赖**：0.3 / 0.4（设计定稿）、0.7（后台 Agent）、0.5（上下文设置）。
**要用户定的**：设计文档里的所有讨论点（占比、转化规则、遗忘规则、隔离规则）。
**验收**：
- 模拟几个月的对话数据跑记忆 Agent：各级记忆的数量和占比符合设计，上下文里的记忆不超预算；
- 遗忘可恢复；
- 旧记忆完整迁移；
- 无痕模式下完全不读写。

### v0.9　书桌独立 + 深度测试

**目标**：书桌成为独立的模块，和对话真正区分开；功能冻结、打磨、深度测试。

**工作项**

- **9.1 书桌定位**（26）
  - 用户的感受：现在「交给 Agent」后还是并进了对话，没有差异。
  - 用户的设想：对话是「在公司工作」，书桌是「在家里的书桌上工作」——一个固定的、相对独立的工作区，有很多想法在这里慢慢积累。
  - 做法初稿：
    - 书桌有自己的常驻 Agent，共享大多数通用设置（模型、记忆模块、技能）；
    - 用户应用内的固定工作区，有自己的记忆分区（用 0.8 的隔离机制）；
    - 任务在书桌里完成，结果留在书桌上，不跳到对话。
  - 0.9 开工前和用户再讨论一次（用户说「我再探索探索」）。
- **9.2 打磨**：各页面的细节、性能（长会话、大量记忆和卡片时的速度）、错误提示、空状态、文档。
- **9.3 深度测试**：用户做一次和 v0.2 一样的深度测试；测试清单包含第 17 条的场景和 0.3–0.8 的新功能；E2E 全部走 OpenCode Go。
- **9.4 修复**：深度测试发现的问题分成「1.0 前必须修」和「1.x」两类。

**依赖**：0.8（记忆分区）、0.7（后台 Agent）。
**要用户定的**：书桌的定位和交互（9.1）；哪些问题必须在 1.0 前修。
**验收**：书桌里交给 Agent 的任务在书桌内完成，不出现在对话列表；用户完成深度测试并给出记录。
