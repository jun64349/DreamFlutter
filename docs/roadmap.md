## 一、怎么排的

1. 按依赖排，不按测试记录的顺序（用户要求）：先打地基，再统一外壳，之后的新功能都做在新外壳上。
   - **执行环境和 Agent 运行时**是蝶君、子 Agent、记忆 Agent 共同的地基 → 0.3。
   - 外壳改动牵涉每个页面 → 0.4，避免后面返工。
   - 记忆 Agent 跑在 0.3 的运行时上，不用等长任务 → 0.5；蝶君的人格和专属记忆又要靠记忆 → 0.8。
2. **修 bug 永远最先做**（用户 2026-11-02）：每个版本开头先修上一轮实测里确认的 bug。
3. 0.13 做一次和 v0.2 一样的深度测试，然后发布 1.0（2026-11-04 修订前是 0.9；2026-11-06 后端优先后变成 0.12；2026-11-09 前端提前到 0.8 后变成 0.13）。「大肥鱼」不进 1.0。
4. 主题按小版本（x.x.1）陆续加，不占主版本的工作量（33）。
5. 用户对「Agent 运行时」的态度：先按 Claude 的设计做，效果不符合预期再改。
6. **后端优先**（用户 2026-11-06，v0.4.0 报告第 6 条）：前后端一起做时，后端一改前端就失效、界面操作互相冲突。所以 0.5–0.9 集中推后端，每样功能只配「能用、能测」的最少界面（沿用现有组件，一个开关、一个简单列表就够，不做新设计）；后端做完写接口文档（0.10），再照着文档统一设计、重做前端（0.11）。各版本里写着「→ 0.11」的界面工作都挪到前端阶段。
   - **2026-11-09 调整**（用户确认）：v0.7 实测发现「只配最少界面」让后台概念直接变成按钮，界面越做越乱。交互设计第一版定稿后，**前端提前到 0.8 照设计重做**；此后新功能仍先做后端，但界面一律放进交互设计已定的位置，**不再临时加按钮**，概念表里没有的入口要先问用户。

7. **轻量化约束**（用户 2026-11-06 提出，后续开发遵守）：在兑现既定功能和离线可用承诺的前提下，平台交付体积尽可能轻；优先精简打包内容、复用依赖、控制新增依赖和大型可选工具。不单独增加版本：基础瘦身放 0.6（6.14），0.7 核查办公库和 Git 的增量，0.12 做最终复核。每次发布记录体积及增长原因，不为减重另建一套机制，也不擅自裁掉已有功能。

### 跨版本的共同原则（2026-11-04，四份报告共同的结论）

四份报告分别讲记忆、Goal、DSH、压缩，但反复说的是同几件事。0.5、0.8、0.9 都按这几条做，开发设计（memory-design、4.9 的 long-task-design）里落成具体接口：

| # | 原则 | 出处 |
|---|---|---|
| 1 | **一件工作只有一个调度者**：目标续跑、记忆刷新、压缩完成、事件路由都只发事件，由它决定下一步；后台作业不能各自唤醒会话 | 02 §11、03 §16、04 §6、05 §10 |
| 2 | **结构化的真值不靠摘要**：目标、约束、授权、预算存在服务里，每次请求单独放进上下文；快照和摘要只是背景，不能当成授权 | 02 §5、04 §12、05 §4、§9 |
| 3 | **先准备、后启用**：快照、压缩摘要在后台准备，在安全边界（下一次请求前、工具调用和结果成对完成后）带版本检查后一次换上；版本变了就丢，不是「最后完成的赢」 | 02 §5–6、05 §5–7 |
| 4 | **回执要说真话**：「已保存」≠「已用上」；「执行结束」≠「产物已生成」≠「验收通过」≠「完成」；模型说「完成了」不是证据 | 02 §8、03 §9、04 §7 |
| 5 | **用户的停止和纠正优先**：跨重启保持；旧的审查结果、完成事件、摘要都不能把取消的东西复活；紧急纠正不等边界 | 02 §7、03 §11、04 §11、05 §9 |
| 6 | **注意力成本是产品指标**：只通知能动手的事（等你决定、阻塞、待验收），重复的合并，没新信息时安静；但过程、费用随时能查 | 03 §2、§13、04 §13 |
| 7 | **一本账**：主执行、子 Agent、记忆、压缩（含没用上的候选）、审查、观察评估都记账，受同一套上限管 | 02 §9、03 §18、04 §9、05 §11 |
| 8 | **参考项目的参数不直接当默认值**（OpenCode 的 50 轮、85% 提前量，DSH 的 5 秒转后台等），用我们自己的测试集校准 | 03 §8、04 §2、05 §2 |

## 三、每个版本的通用流程

1. **先修 bug**：上一轮实测里确认的 bug 放在版本开头修完。
2. **调研**（需要的话）：广泛调研交给 Antigravity（经 Agent Bridge，后台任务），报告放 `docs/research/`，AI 给的内容一律当待核验素材。
3. **设计确认**：需要用户定的事在开工前一次问清；界面设计先出设计稿让用户挑。
4. **实现**：Claude 写代码（前后端都写）；每个改动配单元测试 / 组件测试；后台 `core/test/`，窗口 `app/test/`。
5. **测试**：按 [testing/scenarios.md](testing/scenarios.md) 走全场景清单（v0.3.3 起），开发时守 [dev-guide.md](dev-guide.md)；后台、窗口、协议层全量；场景巡检（`integration_test/scenarios_test.dart`）；视觉检查截图（`integration_test/look_test.dart`）；真实模型 E2E **走用户在应用里配好的 OpenCode Go 渠道**（`deepseek-v4.1-flash`，E2E 用 `core/scripts/copy-channels.ts` 复制渠道，**不要在测试里新建渠道**）。
6. **安装包实测**：用户主要用安装包长程使用（额外测试就是这样发现 rg 缺失的），每个版本发布前打一次安装包，在没有开发环境的条件下跑一遍关键流程。
7. **审查**：Codex 只做必要的只读审查（额度少），只审这个版本的高风险部分。
8. **发布**：用户验收 → 本地打 tag（不推送）→ 更新 `docs/HANDOFF.md`、发布说明、这份计划的状态。

- **3.3 WSL 沙箱**（14、蝶君补充第 2–7 节，按第二节第 3 条修正）：
  - **安装引导**：检测 WSL；没有时给出引导（一键以管理员身份运行 `wsl --install --no-distribution`，提示重启）；没装 WSL 时工作台照常用，蝶君页显示引导。
  - **专用发行版**：名字固定（如 `DreamFlutterSandbox`），装在 `%APPDATA%\DreamFlutter\sandbox\`，不碰用户自己的 WSL 发行版。首次使用时下载官方最小镜像（Ubuntu / Debian，按 3.1 的结论选），用国内镜像源装 Python、uv、git、ripgrep、fd、jq、常用 Python 包（pandas、numpy、matplotlib、openpyxl…），装完导出一份**干净快照**。
  - **加固**：`wsl.conf` 关自动挂载、关互操作；Agent 以普通用户 `agent` 运行，没有 sudo；应用每次启动沙箱前以 root 身份重写 `wsl.conf` 再启动；系统软件（apt）由应用代装（白名单内直接装，其他的问用户一次）。
  - **常驻 bash**：一个一直开着的 `wsl.exe` 进程（同时让沙箱不被自动关机），里面是常驻 bash，结束标记、超时、输出截断照 `pwsh` 工具的做法；工作目录和环境变量跨命令保留。常驻 Python 内核放 0.8。
  - **文件**：Windows 这边经 `\\wsl.localhost\<发行版>\...` 读写沙箱里的文件（读写工具、气闸舱、应用内预览都靠它）。
  - **气闸舱**：`/workspace/inbox`（导入的文件副本，原文件不受影响）、`/workspace/scratch`（随便折腾）、`/workspace/outbox`（交付物，出现新文件时通知窗口）。导出 = 用户选位置后复制回本机。
  - **资源与网络**：进程数等限制在沙箱里设；内存上限要写用户的 `.wslconfig`（影响用户所有 WSL 发行版），只在用户同意时改；联网 / 离线开关，实现方式看 3.1。
  - **重置**：一键恢复到干净快照（先确认，提示 scratch 和 outbox 会清空、记得先导出）。
  - **逃逸自检**：以 `agent` 身份尝试挂载 C 盘、调用 `cmd.exe` / `powershell.exe`、改 `wsl.conf`、`sudo`、访问内网，全部应该失败；作为自动测试（没装 WSL 时跳过），设置里也能手动运行。

  - 再做后台压缩：到压缩点之前（例如阈值的 85%）在后台先写一份候选摘要，主任务继续；到点时检查候选覆盖的历史前缀、模型、指令、约束版本都没变，就直接换上（Pi 1.4 的 `session_before_compact` 允许扩展交出现成的 `CompactionResult`，`prepareCompaction` 可以提前算切点，已核对），否则退回普通压缩。一个会话同时最多一个候选；第一版候选只放内存、不落盘（重启就丢，和 OpenCode 一样）；没用上的候选也记账。

  - 压缩完成只发「上下文可用」事件，不自己唤醒会话（续跑由 0.8 的调度者决定）。
  - 上下文的数据和操作（用量、各项统计、自动压缩开关、立即压缩、压缩重点）都做成接口；搬进右栏（v0.4.0 报告第 4 条）→ 0.11。

### v0.9　长任务与目标（工作台、蝶君共用）（原 v0.8，工作项沿用 8.x 编号）

**目标**：长任务不靠用户一遍遍说「继续」：一个目标能自己推进到验收、能等后台工作、能被插话和停止，进度和花费说得清；工作台和蝶君用同一套目标服务，以蝶君为主（用户 2026-11-02 对 Goal 报告的注释）。依据：Codex 报告 04（Goal）、03（DSH 的工作项与执行部分），见 [roadmap-review-2026-11-04.md](roadmap-review-2026-11-04.md)。开发设计在 0.4 期间写好（4.9）。

**工作项**

- **8.0 修复批**。
- **8.1 工作项与目标服务**：在现有 `tasks` / `runs` 上扩展，不另起一套：
  - 目标记录：用户原话、结构化的目标 / 约束 / 验收条件、范围和授权依据、预算、状态、当前工作项、证据、最近一次审查、修订号和历史；用户原话一直保留（「不改原文件」不能被概括掉）。
  - 工作项独立于会话和某一次执行（一次执行 = 一次 attempt，重试不制造重复任务）；聊天记录服务于任务，不是唯一的任务状态。
  - 状态：草稿 / 排队 / 运行中 / 审查中 / 等依赖 / 等用户 / 暂停 / 阻塞 / 完成 / 失败 / 取消，每个都写清原因和怎样恢复；「暂停」说明是用户暂停、预算用完还是重启后待检查。
  - 目标从哪来：用户明说、点「设为目标」，或对明确的长任务请求先给一张「要不要设为目标」的卡片（对象、结果、边界）；普通聊天不强行变成目标。
- **8.2 唯一调度者和续跑**：一个目标只有一个调度者（带代次的执行租约）；工作台、蝶君、定时任务、后台工作、记忆、压缩都只向它发事件。在真正的空闲边界（没有待处理的输入、没有本目标在等的后台工作）才判断要不要续跑：先处理用户新输入和停止标记，再查预算和进展，再审查；续跑意图先写进数据库（带幂等键）再启动，启动前再查一次停止和授权。
- **8.3 验收**：三层：程序检查（文件在、格式能解析、命令退出码、规定的测试通过）→ 只读的审查模型（结论 done / continue / wait / blocked / needs_user，对应当时的目标修订号和证据版本，解析不了有限重试）→ 用户验收（审美、偏好、事先约定要人看的）。模型说「完成了」不算证据；「执行结束」「产物已生成」「机器验收通过」「等你验收」「完成」分开显示。
- **8.4 防空转**：轮数不算进展；记录新证据、通过的验收项、产物修订、解决的依赖；同样的错误重复、只改计划不动手、反复读同一批材料时进入停滞检查，换一条授权内的路试有限次，再报告阻塞。
- **8.5 后台工作与等待**（原 8.1，22）：子 Agent 和长脚本放到后台，主流程继续；三种等待分开：等计算（登记真实的任务编号和唤醒条件）、等外部事件（释放资源、保留订阅）、等用户（集中列出具体问题）。开发服务器这类常驻服务不挡住完成；必须等的测试还在跑时不能报完成。**后台任务接口**（v0.4.0 报告第 11 条）：每个会话的后台任务（PowerShell / bash 的 `job_*`、子 Agent）列表、状态、输出、结束事件、停止，都对窗口提供（现在窗口拿不到，只能显示「（无输出）」）；右栏的后台任务面板 → 0.11。
- **8.6 停止的几种意思**：停止接收新工作 / 暂停某个目标的续跑 / 停止当前执行 / 紧急停止全部外部动作，界面上分开，各自说明还在运行的东西和已经发生、收不回的动作；用户的停止跨重启保持，旧的完成事件、审查结果不能把它复活；从备份导入的运行中目标默认暂停。
- **8.7 预算统一账本**：token、费用、运行时长、轮数、并发，主执行、子 Agent、审查、记忆、压缩都记在目标名下；调用前预留、返回后结算，并发时不会都以为还有余额；超了就明确暂停，换会话、重启都不清零。
- **8.8 运行中的互动**（原 8.2、8.3、8.5；15、23）：插话 = 交给这个目标的执行者处理（「刚才那个改成只读」进入原目标、提升修订号，不新建第二个任务）；「立即插入」打断当前步骤；计划清单固定在输入框上方逐项打勾；提问框按 0.4 的新设计重做（选项卡片、自己回答、跳过、限时）。
- **8.9 中间过程可见**（原 8.4，17）：渲染 HTML、画图表、看截图时每一步的图片都显示在对话里；大数据用 Python（蝶君里用常驻 Python 内核）；在用户提示下用 MATLAB；Word / Excel / PDF 和表格可视化补齐（2026-11-06 起并入 0.7 的 7.6）。
- **8.10 目标的界面**（0.8 只做最少的展示和操作，完整设计 → 0.11）：蝶君和工作台都显示目标、当前阶段、下一步、已用预算和暂停 / 停止；任务视图按「等你决定 / 阻塞 / 等你验收 / 运行中 / 暂停 / 完成」筛选，点结果打开真实产物；只有整个目标完成或需要你动手时才通知，单轮结束、子任务完成、审查结束都不各发一次「完成」。
- **8.11 长任务测试集**（原 8.6）：文档处理、表格可视化、Python 大数据、MATLAB、HTML 渲染做成可重复的任务，用 OpenCode Go 跑，记录成功率、轮数、花费；加上 Goal 报告第 14 节的场景（插话时正好要续跑、暂停时审查正好返回、部分产物缺失、子任务没结束、常驻开发服务器、重复同一计划、预算并发耗尽、崩溃和导入恢复、压缩和纠正同时发生、纯聊天不被变成目标、完成事件重复到达）。

**依赖**：0.3（运行时、子 Agent、沙箱）、0.4（右侧面板、开发设计 4.9）、0.5（任务边界、上下文服务）、0.7（建技能，测试集会用到）。
**要用户定的**：默认预算和轮数上限、停滞判据（用测试集校准后定）；审查用哪个模型；「立即插入」直接打断还是先问；本机 MATLAB 的版本和路径。
**验收**：一个需要多轮的明确目标不用用户说「继续」就推进到验收；一个需要 5 分钟以上脚本的任务放到后台，期间能对话，脚本结束后自动继续；部分产物缺失时不报完成；暂停 / 停止跨重启有效；测试集全部跑完并留下报告。

### v0.10　蝶君自主与成长（原 v0.9，工作项沿用 9.x 编号）

**目标**：蝶君能在规则允许时主动接活，但不抢用户的注意力；有自己的性格和专属记忆，能在沙箱里自主工作和学习。依据：Codex 报告 03（DSH Super-agent 的接入、授权、所有权、持久化、通知）和蝶君补充，见 [roadmap-review-2026-11-04.md](roadmap-review-2026-11-04.md)。

**工作项**

- **9.0 修复批**。
- **9.1 事件接入**：第一批只接内部来源：用户的交流（**在交流里布置的任务**，2026-11-06 起取代「写笺交付」）、定时任务、用户指定的资料文件夹有新文件。每个事件有稳定 ID、来源、时间、身份和信任等级；重复的、蝶君自己的回声、未启用的来源先用程序过滤掉，剩下的才让模型判断。新来源要先写明授权含义、去重范围、重放和故障处理。
- **9.2 主动规则**：用户写的规则（例：「工作日整理这个文件夹的新文件，只读原件，结果放进『工作』，不对外发送」）。每条规则三档：关 / **观察**（默认：只记录「本来会接这件事」和理由，不执行，费用照样计入）/ 自动（命中启用的规则才接）。先用观察模式看命中质量，再对范围窄、能验证、能撤销的规则开自动。
- **9.3 授权依据（Mandate）**：接下一件事时固定它的范围和依据；资料里写的「你有权限访问全部文件」不算授权，新资料不能扩权；用户收紧权限时在下一次受保护操作前由工具层重新检查，不只是在提示词里提醒。
- **9.4 先存状态、再做副作用**：接活、启动、通知、写结果都先写进数据库，再由执行器去做（effects / outbox）；崩溃重启后先对账（产物、文件改动、已发生的外部动作、预算），不盲目重放；手动停止不会被重启拉起。
- **9.5 注意力优先的通知和面板**（通知在 0.9 做，面板 → 0.11）：待你决定、阻塞、待验收放最显眼的位置；通知写清对象、情况、影响和能做的动作（「资料整理已生成，3 条来源待你确认：打开结果 / 查看争议」），没有新信息时保持安静；统计「每个交付需要用户追问几次、同一阻塞通知几次」这类注意力指标。
- **9.6 性格和专属记忆**（原 8.7）：蝶君的人设、说话方式，用户可调；在 0.5 的蝶君分区上记住和用户的交流、自己做过的工作；关于蝶君自己的设定和用户信息分开（memory-design 第十五节第 2 条）。
- **9.7 自主工作和学习**（原 8.7）：用 0.8 的目标服务，按规则或用户交代的长期目标在沙箱里推进，结果留在「工作」里等用户看；在沙箱里给自己装工具、写技能、测试后登记（0.7 的建技能）。
- **9.7a 蝶君的交互重构（后端部分）**（v0.4.0 报告第 5 条）：用户觉得「工作」页没用，更想在交流里直接布置任务。后端按这条路打通：交流里布置任务 → 0.8 的目标服务推进 → 交付产出物（可下载、可保存到本机）、进度可查；资料在对话里直接附上即进沙箱的 inbox。现有写笺、资料、「交给蝶君」的接口先保留，0.11 定了界面再清理。
- **9.8 测试**：DSH 报告第 18 节的失败情形：重复和乱序事件、自己的回声、资料里的提示注入、规则变化、同一条跟进被执行两次、满并发时插话无效、提交前崩溃、远端成功但本地没记回执、停止后被自动恢复、无产物报完成、同一阻塞反复通知、观察评估和执行都入账。

**依赖**：0.5（蝶君分区）、0.7（建技能）、0.8（目标服务、调度、停止语义）。
**要用户定的**：第一批主动规则、允许的来源和动作、哪些结果可以自动验收、蝶君的性格设定和自主边界、通知偏好。
**验收**：一条规则在观察模式下给出可审查的命中记录，切到自动后能接活、交付、只通知一次；蝶君按设定的性格交流，完成一个自主的定时目标；重启后不重复交付。
