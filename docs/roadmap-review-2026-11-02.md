## 二、对 Gemini 隔离方案的核查

整体方向我认同：**Windows 家庭版上，WSL2 自带的虚拟机是唯一现实的选择**（Windows Sandbox 家庭版没有，Docker Desktop 底下也是 WSL2）。建议采用它的这几块：自己的 WSL 发行版（不碰用户可能装的 Ubuntu）、一个常驻进程保活、`/workspace` 下 inbox / scratch / outbox 三个目录、「文件气闸舱」导入导出、干净快照一键重置、联网 / 离线开关。

但有几处需要纠正或补上：

1. **「沙箱里给 Agent sudo 免密 root」和「物理隔离」互相矛盾。** 方案靠 `/etc/wsl.conf` 关掉自动挂载和互操作，但：
   - WSL2 里 root 可以手动挂载 Windows 磁盘（`sudo mount -t drvfs C: /mnt/c`，微软文档里就有这条命令），自动挂载关了也照样能挂，挂上后就能以用户的身份读写整个 C 盘；
   - root 还可以改 `/etc/wsl.conf`，下次启动就把自动挂载和互操作打开；
   - 网络里的 `iptables` 封内网也一样，root 自己就能删掉规则。
   
   **我的建议**：Agent 用普通用户 `agent`，**不给 sudo**。装 Python 包用 `uv` / `pip --user`、虚拟环境，都不需要 root；真要装系统软件（`apt`），由应用（宿主）代办，按白名单或弹一次确认。应用每次启动沙箱前，以 root 身份把 `wsl.conf` 重写一遍再启动。0.3 写一套「逃逸自检」测试：以 agent 身份尝试挂载 C 盘、调用 `cmd.exe`、改 wsl.conf、访问内网，全部应该失败。这和用户说的「用户之下完整的独立权限」也对得上：是「用户级」，不是 root。
2. **Agent 的「大脑」放在本机后台，只有「手」进沙箱。** Gemini 的代码里 Agent 循环在宿主、工具经管道进沙箱，我同意：Key 永远不进沙箱，模型请求不依赖沙箱联网，Pi、网关、记忆、技能都是同一套。沙箱里只跑命令、Python、文件读写。
3. **常驻进程先不用自写的守护程序。** 我们的 `pwsh` 工具已经是「常驻 shell + 结束标记」的做法（`agent/shell.ts`），0.3 照这个做一个常驻 bash（经一个一直开着的 `wsl.exe` 进程，顺便保活）；文件读写走 `\\wsl.localhost\<发行版>\...`（Windows 直接能访问 WSL 里的文件），气闸舱和应用内预览也靠它。**常驻 IPython 内核**（变量跨轮保留）放到长任务那一版。
4. **「0 毫秒切换、两边常驻」的代价**：WSL2 虚拟机常驻会占几百 MB 到 1 GB 多内存。建议「第一次进蝶君时启动，之后一直开着」，设置里可选「随应用启动」。内存上限要写进用户的 `.wslconfig`，这个文件对用户所有 WSL 发行版都生效，所以只在用户同意时改。
5. **环境镜像从哪来**：Gemini 说预先打包一个 80–120 MB 的镜像。打包这个镜像本身也要在一台装了 WSL 的电脑上做。两种做法：
   - A. 安装包里带做好的镜像（体积大，首次启动快、离线可用）；
   - B. 首次使用时下载官方最小镜像（Ubuntu / Debian 官方），在里面装 Python、uv、git、ripgrep 等（用国内镜像源），装完存一份干净快照（安装包小，首次要联网几分钟）。
   - 我建议 0.3 用 B（先跑通），发布 1.0 的安装包时再决定要不要预制。
6. **装 WSL 需要管理员权限，多半还要重启一次。** 应用里给引导（检测、一键运行 `wsl --install --no-distribution`、提示重启）。没装 WSL 时工作台照常用，蝶君页显示引导。**开发也需要在你这台电脑上装 WSL**——这件事需要你点头，并由你本人以管理员身份执行。
7. macOS 先不管，但接口按「执行环境」抽象（本机 / WSL / 以后的 Mac 虚拟机），后面加不用重写。
8. 蝶君「不弹审批」只覆盖沙箱里的事。**沙箱外有真实后果的事**（MCP 发邮件、社交平台发帖、花钱、调用卡片的本机授权）还是要规则——将来做「大肥鱼」时这是核心问题，0.3 先定：蝶君默认不开 MCP 和会碰外部账号的工具。

## 四、子 Agent：建议和蝶君、记忆 Agent 共用一套「Agent 运行时」

额外 11、蝶君、记忆纪要里的记忆 Agent，本质上是同一件事：**主流程之外，再起一个有自己角色、工具、环境、权限和预算的 Agent**。建议 0.3 打一个共同的地基，三者都建在上面：

- **角色卡**：名字、提示词、模型（可用模型组，子任务用便宜的）、工具、执行环境（本机 / 沙箱）、审批规则、能读哪些记忆、轮数和花费上限、上下文怎么给（全新 / 带父会话摘要 / 分叉）。
- **子 Agent 工具**：主 Agent 派活（可以一次派几个并行），子 Agent 在自己的上下文里干完，只把结果摘要交回，长结果写成文件。右栏显示每个子 Agent 的进度和花费。
- **可能的创新点**（等调研后再定，先列想法）：
  1. **跨环境派活**：工作台的 Agent 可以把「试装一个库、跑一段不放心的代码」这类活派给沙箱里的子 Agent，结果经气闸舱回来——我们同时有本机和沙箱两种环境，这是别的平台没有的组合；
  2. 子 Agent 的产出落到书桌 / 蝶君的「工作」里，成为可复用的资料，而不只是一段聊天文字；
  3. 记忆 Agent 就是一个固定的角色卡，权限由程序锁死（记忆纪要 12.5 的要求）。
- **分批**：0.3 做前台、并行的子 Agent；放到后台、主流程等它完成再继续（原 7.1）还在长任务那一版。
- 调研交给 Antigravity：Claude Code 的子 Agent 与后台任务、Codex、OpenHands、Manus、Kimi 等的多 Agent 做法，以及「有没有适合我们双环境的新做法」。
