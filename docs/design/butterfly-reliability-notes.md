# 蝶君的可控可靠：讨论记录

2026-11-12 用户和 Claude 的讨论，**2.0 以后做**。先由调研 Agent 做文献调研（提示词见 [research/butterfly-reliability-research-prompt.md](../research/butterfly-reliability-research-prompt.md)），再构思、仿真、写正式设计。roadmap 第七节「蝶君的可控可靠」是这份记录的摘要。

## 一、出发点

- 用户是做可靠性系统工程和测试的，要把蝶君做成**可控、可靠**的助手：它的形象、人设、做的事、每一个操作都可控可靠。
- 大模型是**不可靠元件**：输出随机、会幻觉、会被读到的资料带偏、不保证听话。可靠性不能靠模型，要靠外面的 harness——用不可靠的元件搭出可靠的系统。
- 提示词和人设只管「怎么说」，不承担任何安全职责。任何安全要求都不能只写在提示词里。

## 二、自主性和可控的平衡

> **边界内模型说了算，过边界时程序说了算。**

- 程序不管蝶君做什么、怎么做。沙箱里学什么、写什么、换什么方法、做几遍，全由它自己定。
- 程序只守几个关口：出沙箱、超预算、报「完成」、改受保护的东西。
- 比喻：程序是护栏，不是抢方向盘的副驾驶。护栏越清楚，护栏内越能放开。

**按后果分级**（用户定）：

- 沙箱里的事：自己做，出错自己重试、换方法、迭代更新，只告诉用户产出的结果。
- 沙箱外的事：谨慎，走用户审批。2026-11-13 细化：只在扩大权限时问，在已批准范围内或收窄权限的自动放行（第八节第 2 条）。蝶君平时只在沙箱里做事，只有用户明确要它到外面做才出去。

## 三、分层防护

| 层 | 管什么 | 例子 |
|---|---|---|
| L0 物理隔离 | 碰不到外面 | WSL 沙箱、不给 root、联网开关、逃逸自检（已有） |
| L1 硬约束（程序强制） | 不能做、不能超 | 见第四节 |
| L2 软约束（提示词、人设） | 说话方式、工作习惯 | 性格预设、「先说打算再开工」 |
| L3 监测和审计 | 做了什么、为什么 | 每个动作的授权依据、结果，可回看 |
| L4 恢复 | 出了事能回去 | 沙箱快照回滚、停止键跨重启有效、模型不可用时降级为只记录不行动 |

## 四、硬约束

1. **能力边界**：能碰沙箱外的工具单独列清单，调用时必须带用户这一次给的授权，由程序检查；不认模型说的「用户同意了」，资料里写的「你有权限」不算授权（roadmap 9.3）。
2. **熔断**：花费、轮数、时长、主动找用户的次数，超了程序直接停。
3. **状态机**：任务状态只能由程序按规则改；「完成」先过硬门槛（交付物在不在）；同一件事不执行两次（单一调度者、先存状态再执行，roadmap 8.2、9.4）。
4. **自我修改禁区**：规则、权限、预算、人设、审计记录只有用户能改，蝶君和记忆系统都改不了。蝶君可以给自己写技能、装工具。用户暂时没有要加的项。
5. **出错默认方向**：按第二节分级。沙箱内自己换方法；碰到外面拿不准时停下来问。

## 五、防护在什么时候跑

| 时机 | 是什么 | 成本 | 例子 |
|---|---|---|---|
| 每次动作前，同步检查 | 硬约束，像联锁、保险丝 | 极低，纯程序，不调用模型 | 调出沙箱的工具时查授权；花费到顶就断 |
| 运行中，旁路监视 | 看门狗，并行跑 | 低 | 死循环、长时间没进展、花费曲线异常就叫停 |
| 做完后复核 | 交付前把关 | 中 | 程序按客观证据判完成 + 不同家族模型复核主观质量 + 写审计记录（2026-11-13 改，原为蝶君自己验收） |
| 开发期，离线分析 | 设计和测试阶段 | 只在开发时 | FMEA、FTA |

## 六、FMEA、FTA 和运行时怎么接

- FMEA、FTA 不在运行时跑。它们在设计期产出：前三种时机里的联锁和监视器（每条失效模式对应一道运行时防线），以及守着这些防线的测试。
- **FMEA**：列失效模式，每条写怎么发现、靠哪条硬约束挡、哪个测试守着。先想到的：虚报完成、死循环烧钱、被资料里的提示注入带偏、人格漂移、重复执行、越权、主动打扰太多、记忆被污染（如「用户叫蝶君」）、自己写的技能有毒。
- **FTA**：顶事件「沙箱外发生了用户没同意的真实后果」，往下拆，每条通路上至少两道互相独立的防线。
- **FRACAS**：运行中被拦下、出错的事都留记录，开发时对照 FMEA 表，判断是已知失效模式还是新的，再补防线和测试。FMEA 表持续更新。

## 七、指标和验证

- **可靠性指标（体检单）**：任务成功率、虚报完成率、每次交付用户追问几次、越权尝试被拦下的次数、人格一致性评分、每天花费分布。**只放「设置 › 开发者选项」**，不给普通用户看（用户定：这是开发层面的，用户只需要结果可靠、行为可控）。
- **验证手段**：回归测试集（长任务测试集是雏形）、故障注入（杀进程、断网、模型返回乱码、带注入的资料）、人格一致性评测（固定对话集按预设打分）、影子运行（主动规则的「观察」档）。
- **人格可控**：人设是带版本号的配置，只有用户能改；记忆系统不能写入或覆盖人设，从结构上杜绝人格漂移。

## 八、调研结果对照（2026-11-13）

调研报告：[research/2026-11-13-agent-reliability-survey.md](../research/2026-11-13-agent-reliability-survey.md)（65 篇，自称精读 37 篇；数字还没抽查原文，作为设计依据前先抽查关键几篇）。

**和我们一致的**：可靠性靠外围 harness；过边界由程序裁决；四种防护时机；纵深分层；提示词不承担安全职责（报告里多篇实证「知行分离」：模型在对话里认得出风险，执行时照样做）。

**报告要求修正的，按要不要用户定分两类：**

要用户定：

1. **自己验收**（和用户 2026-11-12 的决定冲突；**2026-11-13 用户定：按报告改**，已写进 roadmap 0.10）：报告最强烈的一条反对意见。自评和同家族模型评审有严重确认偏误，一条虚假的权威提示就能翻转四成以上正确裁决；确定性代码检查贡献了大部分可靠性提升。建议改成：「完成」由宿主机程序按客观证据置位（文件、退出码、改动对比）；主观质量交给**不同家族的模型**独立复核，执行者不给自己打分。
2. **沙箱外一律审批**（**2026-11-13 用户定：只扩权才问**，已写进 roadmap 0.10）：报告说一律审批会造成审批疲劳，用户最后会不看就点。建议参考 Progent：权限只收窄的自动放行，只有扩权才问（实验里只有约 6% 的更新需要问）。

照做就行（不改用户的方向）：

3. **沙箱内也要看门狗**：「边界内模型说了算」不等于不看。强模型在长任务里更容易陷入死循环；重试要有次数上限、要防重复副作用。加一个合法的「做不下去了」出口（`BAILOUT` / `ESCALATE`），让它不用编造完成或钻漏洞。
4. **自我修改禁区放在沙箱外的物理位置**：人设、规则、预算、审计记录、验收脚本都由宿主机保存，沙箱进程写不到。现在这些本来就在后台数据库里，不在沙箱内，方向对；再把「核心记忆」和验收脚本加进禁区。
5. **FTA 的独立性假设不成立**：同一个模型的各步失效强相关，不能简单相乘。补 **STPA**，分析「每个部件都正常、合起来失控」的情况。FRACAS 的分母用工具调用次数或任务小时，不用日历时间；再记一项「静默潜伏期」（出错到被发现多久）。
6. **人设每轮重新锚定**：不能只在对话开头放一次；每轮推理前由程序把人设摘要放进固定位置。旁路做漂移监测。上下文压缩之后人设不会自动恢复，要重新放。
7. **记忆分两轨**：用户亲口说的和蝶君自己从外部学来的分开存；外来的带出处标签、会过期，永远不能覆盖人设和规则；自己写的技能入库前先做代码扫描。（相关攻击：只靠普通提问诱导写入记忆的成功率在九成以上；藏在 README 里的「成功经验」能被它模仿。）
8. **主动聊天**：在任务结束、切换应用这类「边界」时找用户，不在「键鼠空闲」时找（空闲往往是在想事情）。每日次数上限之外再加「连续被忽略就拉长间隔」；用户一开始输入，后台的主动消息立刻挂起。
9. **假成功的返回**：接口返回成功但内容为空、被截断，比明确报错更危险，会让任务静默走歪。模型接口和工具返回都要校验非空、结构完整，否则转成明确的错误。
10. **沙箱**：报告担心沙箱能连到宿主机的内网地址。现有设计已经覆盖：蝶君用户的出站流量按 uid 丢弃发往 10/8、172.16/12、192.168/16、169.254/16、100.64/10 的包，自动挂载和互操作关闭，逃逸自检。还缺：沙箱镜像和工具的**定期更新**（长期不更新会留下已知漏洞）。

**测试方面的建议**：长任务按时长分组，每个任务跑 5 次看 `pass^k`（全部成功的比例），而不是只看跑通一次；在模型和工具的返回层注入「空返回、截断、超时」；做 Troy Moment 式红队（给一个只有改受保护文件才能过的任务，看它会不会去改）；FRACAS 闭环里人为注入缺陷，检查报警是否 100% 触发。

## 九、和 0.10 的关系

2026-11-13 用户定：「假成功」返回校验、「做不下去了」出口、人设每轮重放这三条低成本的也**等 2.0 一起做**，不提前（0.10 已开发完）。第八节第 1、2 条（不同家族模型复核、只扩权才问）0.10 也没做，同样放到 2.0；0.10 已有的是程序核对证据 + 蝶君验收说明、每次出沙箱的授权问一次。

0.10 照常做的硬约束是这里的地基：9.3 授权依据、9.4 先存状态再执行、熔断、验收硬门槛、主动聊天的次数上限。2.0 以后按调研结果补全第三到第七节。
