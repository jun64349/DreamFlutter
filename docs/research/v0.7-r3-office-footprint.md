## 3. 三档组合的真实去重结果

| 档位 | 组成 | W 新增 bytes / MiB | L 新增 bytes / MiB | W 库负载 ZIP MiB | 镜像 gzip 新增 MiB |
| --- | --- | ---: | ---: | ---: | ---: |
| 精简 | python-docx + openpyxl + python-pptx + pypdf | 30,446,727 / **29.04** | 5,694,761 / **5.43** | **12.18** | **1.17** |
| **推荐** | 精简 + pandas + matplotlib | 150,231,893 / **143.27** | 5,694,768 / **5.43** | **46.86** | **1.17** |
| 候选完整 | 推荐 + pdfplumber + reportlab | 184,633,666 / **176.08** | 65,387,867 / **62.36** | **63.19** | **24.83** |

“精简”与“推荐”的 L 差 7 bytes，来自临时 venv 路径长度等安装元数据，不是重复安装 pandas/matplotlib。空增量库的 ZIP 容器仍有 22 bytes 头尾，表中按 **0** 计新增内容。

**推荐档理由**：四种主格式加数据处理和图表均有入口，pandas 与 matplotlib 在 W 共享 numpy 等，W 的组合成本低于各行相加；L 可以完全复用数据/图表栈。精简档使工作台缺少通用数据与图表库，只适合用户明确接受更窄能力时选；候选完整档增加精细 PDF 提取和 PDF 排版，但两端约多 90 MiB 的新增库逻辑字节、镜像压缩多约 23.65 MiB，当前不建议默认全部带。

推荐档是在 Claude“主力 Office 库 + pandas”建议上补 matplotlib，因数据图表属于常见交付且 L 已有；“精简+pandas、不带 matplotlib”的中间组合未单独测量，不给它虚构精确差值。用户也可要求补测该档；本轮三档已完整测量，不据此替用户决定。

## 4. 压缩镜像增量如何实测

为避免“wheel 压缩体积”冒充“镜像增长”，另外读了原始镜像的 70,030 个 tar 成员，保留其内容到最后一个有效成员。用同一 `zlib` gzip level 6 压缩基线；复制压缩器状态，分别追加每个真实安装的增量文件（研究路径 `/opt/dreamflutter/office/`），再写规范 tar 结束块。所有处理和派生压缩文件都在 Windows 临时根内。

- 同口径重压缩基线：**472,087,526 bytes**，不是原文件 472,724,239。重压缩本身少的 636,713 bytes 不算库“减重”。
- 推荐档追加后的压缩流为 **473,315,734 bytes（451.39 MiB）**，对照增量 **1,228,208 bytes（1.17 MiB）**；精确逐项值见 `sandbox-image-results.json`。
- 实际写出推荐档派生 tar.gz，再完整读取，核对新增文件数 **364**；原始随包 tar.gz 的 hash 保持一致。
- 逐库与三档的 gzip 增量都按“新流减同口径基线”计算，已复用项为零。此法实测的是**基于真实安装文件的研究 overlay**；不代表已完成正式镜像的库位置、Python 导入路径和 CLI shebang 接线，也没有启动这个派生镜像作为产品。

W 的“库负载 ZIP”采用 deflate level 9，仅打包空 venv 之后新增文件，保留依赖/许可证等；**不是最终安装包差值**。最终 Velopack 包、trim 策略、压缩字典、安装后缓存、WSL VHD 实际分配及 clean 快照副本要在用户选档并实施打包后重测。本轮不动打包脚本，不能声称已有最终 v0.7 安装包大小。

## 5. 已验证到哪里，哪些承诺仍需补齐

正式测量共 **22 个环境案例通过**（8 个独立候选 + 3 档，W/L 各 11）；另有现有沙箱 11 项预测，不混入正式分母。通过的是代表性结构/数据任务，未做 Word/PowerPoint/Excel 原生打开或页面渲染验收；图表只测英文标签 PNG，中文字体/排版效果和美观规范留第二波内置技能验证。100k 行不等于任意规模都能装进内存；更大文件应分块读写，按实际任务测峰值内存。

**选定上述任一档，都还没有覆盖 roadmap “读写和转换”的全部可能含义**：

- 可直接做：DOCX/XLSX/PPTX 结构读写、CSV↔XLSX 数据转换、PDF 分合页/文本提取、图片图表；具体复杂功能仍需代表性样本。
- 未覆盖：DOC/XLS/PPT 旧二进制格式；Office→PDF/图片的保真渲染；公式重新计算；PDF→可编辑 Office 的高保真还原；扫描 PDF 的完整 OCR 流水线；任意 PDF 版面编辑。
- 现有 Node PDF 读取、Linux Tesseract 可复用各自环节，不会自动变成完整转换流水线。LibreOffice、独立渲染器或其他后端的体积与任务未在本轮实测，不能把 reportlab 或 python-docx 当作等价替代。

因此在 [决定备忘 Q72-04](v0.7-decision-memo.md) 中单列转换范围：由用户/Claude 明确首版格式与保真程度，并派必要转换后端的补充实测，**不因减重擅自删去已承诺的能力，也不把缺口标为 7.6 完成**。

## 6. 复现入口

1. 从证据 JSON 读取固定 root/依赖版本、官方 wheel 文件名/hash；W 使用原便携 Python，L 使用 hash 匹配的原始镜像，避免动态 latest 导致结论漂移。
2. 把脚本 `.txt` 快照复制到新的唯一临时根并改路径后运行；先取 wheels，再 `--no-index` 安装；L 以临时镜像的普通 uid 运行并复用 system-site-packages。证据目录中的脚本不会在仓库中执行。
3. 检查每条安装日志、smoke 断言、`addedBytes/modifiedDeltaBytes` 与组合；压缩实验用相同参数比较基线和变体。保留许可证，不删除依赖文件来凑小数。
4. 正式打包后另跑干净环境 offline 验证：默认 `python` 可 import、两端代表性任务、中文字体/渲染及转换清单；这一轮数字只能支持选型，不能替代接线和最终包验收。
