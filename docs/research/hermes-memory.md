- 结论先说：Hermes 的内置记忆**很简单**（两个小文本文件），它的长处不在记忆的结构，而在**围绕记忆的工程细节**：什么不该记、写入怎样不出错、压缩前先存档、后台复盘、技能的生命周期管理。我们的三级记忆设计在结构上已经比它完整得多（层级、来源、版本、批次回撤、作用域）；值得借的是它踩坑后加上的那些规则。

## 一、Hermes 的记忆由哪几部分组成

| 部分 | 是什么 | 要点 |
|---|---|---|
| 内置记忆 | 两个文件：`MEMORY.md`（Agent 的笔记：环境、约定、学到的东西，上限 2,200 字符）和 `USER.md`（用户画像：偏好、沟通方式，上限 1,375 字符） | 合计约 1,300 token。会话开始时读进系统提示词，**整个会话内冻结不变**（保住提示词缓存）；会话中写入的内容立刻存盘，但要下一个会话才看得到 |
| `memory` 工具 | 主 Agent 自己增、改、删条目 | 新版只有 `add` / `patch` / `remove`，可以一次提交一批操作；没有「读」，因为内容已在提示词里 |
| 会话搜索 | 所有会话存在 SQLite，FTS5 全文检索，`session_search` 工具 | 返回原始消息，不经模型总结；记忆装不下的细节靠它找回 |
| 后台复盘 | 每隔若干轮，分叉出一个后台 Agent 回看对话，决定要不要存记忆、改技能 | 用同一模型时复用提示词缓存；可改用便宜模型（只给最近几轮原文 + 更早部分的摘要）；可设单次复盘的输入上限；可关掉 |
| 写入审批 | `write_approval` 一个开关，前台和后台都管 | 打开后后台写入先「暂存」，用户 `/memory approve` 才生效 |
| 外接记忆插件 | Honcho、Mem0、Hindsight、Holographic 等 8–9 个，**和内置记忆并行**，不替代 | 每轮前预取相关记忆、每轮后同步、会话结束时提取、内置写入镜像过去；压缩前回调 |
| 技能管理员（curator） | 后台定期维护「Agent 自己创建的技能」 | 按使用情况 活跃 → 30 天未用变「陈旧」→ 90 天未用归档；从不自动删除；可钉住；有快照和逐条回滚 |
| 学习时间线（`/journey`） | 按时间展示学到的技能和记忆，可删、可改 | 界面上的「回顾和修剪」入口 |

## 二、Hermes 怎样「遗忘」

Hermes 没有一个叫「遗忘」的模块，遗忘散在几处：

1. **内置记忆满了就逼主 Agent 当场腾地方**：写入超过字符上限时工具报错，把现有条目全部列出来，要求 Agent 在同一轮里合并或删掉一些再写（新版要求「一批操作里先腾出至少 N 个字符再加」）。不自动压缩、不悄悄丢弃。
   - 问题：遗忘由主 Agent 在干活中途、在容量压力下顺手决定，删了就没了（内置记忆没有版本和回撤）。这正是我们纪要 §11 明确不要的做法。
2. **Holographic 插件的「可信度 + 时间衰减」**（纯本地）：
   - 每条事实有可信度（默认 0.5）。Agent 用了以后反馈「有用」+0.05、「没用」−0.10（**负面反馈比正面重一倍**）；检索时可信度低于 0.3 的不返回。
   - 时间衰减**只影响检索排序**，不删除：得分 × 0.5^(距上次更新的天数 ÷ 半衰期)，默认关闭。
   - 矛盾检测：两条事实**涉及的实体高度重合、内容却很不一样**，就列为可能矛盾（不调模型的廉价预筛）。
3. **技能管理员的生命周期**：只管 Agent 在后台自己创建的技能（用户要求建的、手写的、内置的、从市场装的都不碰，除非用户把它「交给」管理员）。
   - 30 天没用 → 陈旧；90 天没用 → 归档（可恢复）；从没用过的至少保留到 30 天才可能归档（「零使用是没有证据，不是没有价值的证明」）；被定时任务引用的、钉住的不动。
   - 每次运行前给整个技能目录打快照；每次改动都记一条审计记录（谁、做了什么、前后文件的哈希），可以只撤销其中一条；归档的东西默认永久保留，只有用户明确执行「清理」才按保留期删除，删除前也先留底。
   - 用模型做的「合并整理」默认关闭（费钱、改动大），默认只做按时间的确定性处理。
4. **「不该记」的规则**（后台复盘的提示词，`background_review.py`）：明确列出不要存成规则的东西：
   - 环境造成的失败（缺软件、刚装好的报错、路径不对、没配置凭据）——用户能修好，不是长期规律；
   - **对工具的否定结论**（「浏览器工具不能用」「X 坏了」）——它们会固化成 Agent 拒绝做事的理由，问题修好几个月后还在引用；
   - 重试就好了的临时错误；
   - **没解决的失败被写成「推荐做法」**——会话里试了几种都不行，不能把这串失败包装成经验；
   - 一次性的任务经过。
   - 环境问题要记的是「怎么修」（安装命令、配置步骤），不是「这个不能用」。

## 三、最近的改动里值得注意的（0.21.0 → 2026-11-05 主干）

- **去掉了「整条替换」**：旧的 `replace` 会把匹配到的整条记录换掉，模型拿它当查找替换用，结果把同一条里的其他事实一起抹掉了。现在只有 `patch`（只换指定的一段，其他保留）。教训：一条记录塞多个事实，任何修改和遗忘都容易误伤。
- **暂存的修改锁定目标原文**：后台暂存的 `patch` / `remove` 记下它针对的那条完整原文；审批时如果那条已经变了，就拒绝执行、留给用户处理（和我们设计里的 `base_version` 是同一个思路）。
- **「记忆需要会话边界」**：整套机制围绕「会话结束」运转；一个会话连续开几周，记忆和会话搜索几乎派不上用场。官方建议在任务完成、换话题、新的一天时开新会话（我们 memory-design 第十六节的任务边界协议是更系统的做法）。
- **「说记住了但没存」是最常见的问题**：模型回答「好的我记住了」但没调用工具，下次就忘了。官方的排查第一步就是看文件里到底有没有（我们的「两张回执」原则正对着这个问题）。
- 复盘的成本控制更细：同模型复盘不能单独降低思考档位（会破坏缓存复用），要省钱就降频率或换模型；单次复盘的输入总量可设上限。

## 四、压缩和记忆的关系

`memory_manager.on_pre_compress`：压缩前先通知记忆插件，让它从**即将被总结掉的那段对话**里存档（「检查点」）；如果要求存档而没有插件成功，**就不压缩**，保留原始对话。目的：压缩不能成为一条「意外遗忘」的途径。

我们这边的差别：我们的压缩不删除会话文件里的原文，记忆提取按游标从会话文件增量进行，所以压缩本身不会让原文丢失；但要保证**提取游标不会因为压缩而跳过被总结的那一段**，以及压缩摘要不把已失效的内容带回来（memory-design 6.3 已有）。

## 五、侧边问题（`/btw`，和我们的侧边对话对应）

- 基于当前会话的快照回答一个旁支问题，**不写入会话、不改变提示词缓存**；工具全部禁用；最多 3 轮。
- **花费记到主会话名下**（和用户 2026-11-06 定的「侧边对话算进统计」一致）。
- 不保存记录（用户要求我们的侧边对话保存、挂在原对话下面，这一点我们比它多）。

## 六、对我们有用的，和不该照搬的

**可以借鉴**（具体落到哪见 memory-design 第十七节草案）：

1. 「不该记」的清单，尤其是**对工具和环境的否定结论要有有效期、遇到反例就推翻**。
2. **一条记录只放一件事**（原子条目）：修改、推翻、遗忘才能精确，不误伤同一条里的别的内容。
3. 程序侧的**矛盾预筛**（实体重合 + 内容差异大），给记忆 Agent 减少工作量。
4. **负面证据比正面证据分量重**（被纠正、被推翻的影响大于「又被用了一次」）。
5. 暂存修改锁定目标原文、审批时核对（我们已有 `base_version`，确认一致）。
6. 写入和加载时的**安全扫描**：记忆会进入每次的上下文，被写进去的提示注入会一直生效、而且很难被「忘掉」。Hermes 在写入和加载两处都检查注入、外泄模式和不可见字符；我们现在只查密钥。
7. **「说记住了但没存」的检测**：模型回复里说了「记住了」，但这一轮没有任何记忆操作 → 程序标记出来。
8. 技能（0.7）的生命周期管理：区分「谁的技能」（用户的、Agent 自建的、内置的、市场装的）、陈旧和归档、钉住、被定时任务引用就保护、运行前快照、逐条审计和撤销、清理只能用户明确执行。
9. 后台复盘可以换便宜模型、只给摘要加最近几轮；单次复盘设输入上限。
10. 学习时间线（界面，0.11）：按时间看学到了什么，能就地修改和删除。

**不该照搬**：

- 极小的硬上限 + 主 Agent 干活中途当场删条目：和纪要 §11「只有真正满了才考虑主动遗忘、要留痕可恢复」相反。
- 按「多久没用」自动归档**记忆**：纪要 §11.5 已定「长期未被调用只能作为复核线索，不能单独证明没有价值；被反复展示也不能增加保留价值」。Hermes 只对**技能**这样做，而且只对 Agent 自建的技能。
- 整条替换式的修改。
