# 一、起点：先精读这篇文章

Anthropic, "The components of agent memory"
https://www.anthropic.com/research/components-of-agent-memory

我已读过，要点如下（请你自己读原文核对，不要只依赖我的摘要）：
- 定义：Agent 记忆 = 从经验（和用户的交互、被派的任务）里得到、跨会话保留、以「可以读回的上下文」形式存放的知识；不含改权重、单次对话内的上下文学习、压缩（compaction）。
- 记忆是一种预测：写下一条规则，就是预测以后会再用到它。较强的模型能形成「失败 → 提出假设 → 验证 → 写成带依据的规则」的闭环（CL-Bench 1.0 数据库任务）。
- 显著性判断：宝可梦实验里弱模型什么都记（413 个文件、1 枚徽章），强模型只记「屏幕上读不到、只能自己想出来」的东西（策略、计划、验证过的规则；9 个文件 + 一个 global.md 仪表盘、4 枚徽章）。能从环境直接读到的状态不该存。
- 引导方式：告诉模型记忆是干什么用的，而不是规定怎么用；对强模型，固定规则（如「只记失败」）反而削弱收益；对弱模型，提示「答题前先读记忆、并验证假设」能让分数接近翻倍。
- Dreaming（借鉴人睡眠时海马体回放巩固；引用 Letta 与 UC Berkeley 的 sleep-time compute）：空闲时回看日志/会话记录来整理记忆，具体作用有
  1. 纠错：拿原始会话记录当事实依据核对笔记（Mt. Moon 例子）；
  2. 构建新的记忆表示，如 Claude 维护的 wiki（互相链接的主题页）。约 35 万文件 / 4.2 亿 token 的公司内部语料、25 题：dreaming 从 2 轮到 128 轮，只用 wiki 的得分 13%→48%；wiki+搜索 54%→61%，只用搜索 53%；wiki+搜索每题省约 2 万 token；
  3. 跨文档综合类问题 wiki 明显更好（并购问题 87% vs 只搜索 73%），单文档就能查到的任务 wiki 无明显收益；还出现 wiki 比原文还大的「博尔赫斯地图」问题；
  4. 把笔记提升到记忆层级顶端、由 harness 在每次会话开头预加载；顶层必须小（Claude Code 的 auto memory 只加载 MEMORY.md 前 200 行或 25KB，作为索引），细节下沉、留链接；
  5. 让记忆围绕特定目标生长：多个 Agent 同写一张共享表导致事实丢失（57 条只留 41 条）；改成「每份合同一页、一个 Agent 负责、原文逐字引用」后 57/57；这个改进是通过「反思失败 → 改建 wiki 的指令 → 重建」的循环找到的；
  6. 跨会话补缺：修死链、合并重复、补索引页。
- 开放问题：何时写记忆（会话中写分散注意力，后台写又不能立即可用）；如何保持记忆最新（dreaming 要算力，应优先核对易变信息、按访问频率调节节奏）；是否以「会话记录搜索」为记忆的根基，再叠加 wiki 等表示；维护表示本身要防止错误和幻觉累积。

请把这篇文章拆解清楚，并追溯它引用和提到的东西：sleep-time compute 原论文、CL-Bench、Harvey LAB benchmark、Claude Managed Agents 的记忆目录、Claude Code auto memory、Anthropic 提到的 dreaming / knowledge wiki cookbook，以及 Anthropic 此前公开的相关能力（memory tool、context editing、Contextual Retrieval 等）。拿不到原文的标「未核实」。

# 二、背景（只作为调研的落点，不需要你评价这个项目）

我们在做一个本地优先的 Windows 桌面 AI 助手平台：
- 架构：Flutter 桌面窗口 + Node.js（TypeScript）后台核心，Agent 运行时基于开源的 Pi Agent SDK；数据放本机 SQLite（一个后台数据库）和会话文件；主要用 DeepSeek 等第三方模型（能力不一定是最前沿，也可能换成别家），每次调用都记账、有预算上限。
- 两个工作面：「工作台」（操作用户真实文件，受审批控制）和「蝶君」（一个常驻、高主动性的 Agent，在隔离的 Linux 沙箱里自主工作，有自己的记忆分区）。
- 现有记忆（已实现）：
  - 三级记忆：一级近期（约 14 天重点管理）、二级阶段、三级长期；每条记忆有类型（偏好/背景/经验/决定/进展/约定/观察）、作用域（全局/工作区/共享组/蝶君）、可信度（用户明说/用户确认/Agent 推测/工具验证…）、状态（候选/有效/待复核/过时/被替代/被推翻/归档/软遗忘）、有效期、来源（指回会话条目，只存短摘）、版本历史、关系（提炼自/替代/冲突/推翻）、操作日志（按批次可整批撤销）；
  - 一个专门的「记忆 Agent」（权限由程序锁死，只能提操作、由程序校验后提交）负责提取、分层整理、去重、冲突处理、准备快照素材；按任务结束、每周、每月、每季度和事件触发排队运行——这和文章的 dreaming 很像；
  - 「快照」是日常起作用的主要方式：任务开始时按预算（默认约 2000 token，且不超过上下文窗口的 3%）把常驻条目 + 相关记忆 + 补充注入上下文；相关性目前只用三元组文本相似度，**还没有语义检索、没有全文索引、没有资料库**；
  - 已做的防护：压缩时不把快照写进摘要（防止被纠正的事实复活）、用户纠正立即替换快照、任务边界才刷新快照、遗忘机制（入口不记、有效期、回想时再巩固、负面证据权重更高、程序预筛矛盾、软遗忘可恢复、彻底删除只留哈希防止再提取）、「为什么没想起来」可查；
  - 原则：约束靠程序，不靠提示词；记忆改动默认自动生效但全部留痕、可撤销，用户能查改删；锁定的不自动改。
- 未来要做的（这次调研的目标）：一个**大型资料库**，作为基座平台的**内置功能**（不是可选插件）：用户导入的笔记、论文、PDF、Office 文档、网页、代码仓库、图片截图等，规模可能从几千个文件到几十万个文件、几十 GB；Agent（工作台和蝶君）要能在上面检索、综合、引用出处，并且资料库和「经验记忆」「历史会话」能协同。还没开始设计。
- 运行环境假设：普通 Windows 笔记本（约 16GB 内存，可能没有独立显卡），要能离线工作；可以随应用附带本地小模型（我们已经计划附带本地语音识别模型）；云端服务只能作为可选增强，不能是必需。中英文混合内容为主。

## A. 拆解 Anthropic 的记忆架构
1. 文章里的「组件」到底有哪些（笔记、显著性判断、注入层/索引、wiki 等表示、dreaming 的各项作用、会话记录作为事实依据）？画出它们的关系和数据流。
2. 每个结论的证据强度如何（样本量、任务类型、模型差异）？哪些结论依赖「强模型」，在能力较弱或不同厂商的模型上可能不成立？
3. 和 Anthropic 已有产品能力（Claude Code auto memory 的 MEMORY.md 索引、memory tool、Managed Agents 记忆目录、context editing、Contextual Retrieval）怎么对应？
4. 这套思路和我们现有设计逐项对照：哪些我们已经有（例如记忆 Agent ≈ dreaming、快照 ≈ 注入层）、哪些缺（例如拿原始会话记录核对笔记、wiki 式表示、会话记录全文检索作为根基、按访问频率调节整理节奏）、哪些我们的做法和它冲突（例如我们用固定的记忆类型和规则，而文章说对强模型固定规则有害）。

## B. 业界和学界的记忆系统全景
1. 梳理主要方案并做对比表：Letta/MemGPT 及 sleep-time compute、Mem0、Zep/Graphiti（时序知识图谱）、A-MEM、MemoryOS 类、LangMem、Cognee、OpenAI/Google 等产品级记忆、Hermes Agent 的记忆，以及你检索到的近两年其他代表性工作。维度：记忆单元形态（条目/文件/图/wiki）、写入时机（会话中/后台）、整理与遗忘、检索方式、时间与版本处理、规模上限、评测结果、是否适合本地部署。
2. 记忆相关的评测基准（如 LongMemEval、LoCoMo、MemoryAgentBench、CL-Bench 等，以实际存在为准）测的是什么、各方案成绩如何、这些基准的局限。

## C. 大型资料库的检索与知识组织
1. 「Agent 自主搜索（grep/全文检索 + 多轮探索）」和「传统向量 RAG」和「预先构建的知识表示（wiki、GraphRAG、LightRAG、HippoRAG、RAPTOR 等）」各自适合什么问题？有没有对照数据？何时值得花算力预先构建表示（文章的结论是跨文档综合有用、单文档查找没用）？
2. 混合检索的现行最佳做法：BM25/全文索引 + 向量 + 重排序、上下文化分块（Contextual Retrieval）、late chunking、多向量（ColBERT 类）、查询改写、引用和溯源。中英文混合时要注意什么？
3. 本地可运行的组件选型（给具体候选、许可证、资源占用、在 Node.js/Windows 下的可用性）：
   - 本地 embedding 和 rerank 模型（中英双语、CPU 可跑、量化后大小）；
   - 可嵌入的索引/存储（SQLite FTS5、sqlite-vec、LanceDB、usearch 等，或你发现的更好的）；
   - 文档解析（PDF、Office、网页、代码、图片 OCR）的本地方案。
4. 规模和工程：从 1 千、10 万到 100 万文件、几十 GB 时，建索引的时间和磁盘占用、增量更新（文件监听、改名移动、删除）、去重、后台限速不卡机、断点续建、索引损坏恢复。有公开数据就给数据。
5. 预先构建的表示（如 wiki）如何控制成本和体积（避免「比原文还大的地图」）、如何衡量它是否在「抽象」、如何防止错误和幻觉在表示里累积、多 Agent 并行构建时怎么避免互相覆盖（文章的「一页一个负责者、原文逐字引用」）。

## D. 记忆、资料库、会话记录三者的边界和协同
1. 「经验记忆」（从交互中学到的）、「资料库知识」（用户导入的文档）、「历史会话」（原始记录）应该是一个统一存储还是分开？各方案怎么做？推荐什么，为什么？
2. 记忆层级怎么设计：哪些常驻注入（必须小）、哪些按需检索、哪些只作为可核对的原始依据？索引页/仪表盘（类似 MEMORY.md、global.md）怎么维护？
3. 资料库里的事实和记忆冲突时（例如文档过时、用户说法变了）以谁为准、怎么标注？
4. 作用域和隔离：工作区、全局、蝶君分区之间资料库怎么共享和隔离；派生表示（wiki、索引、摘要、缓存）怎么继承作用域。

## E. 维护与正确性（dreaming 怎么做才可靠、可控、花得起）
1. 后台整理的触发、节奏和预算：如何优先处理易变信息、按访问频率或「最近被用错」调节；增量 vs 全量；有没有成本/收益的数据。
2. 用原始记录核对笔记的具体方法；派生内容的出处追踪（每句话能指回原文）；自动化的一致性检查（死链、重复、矛盾、过期）。
3. 删除和遗忘在大规模下怎么传播：用户删除一份文档或要求彻底忘掉某事时，索引、向量、wiki、摘要、记忆里的派生内容怎么一起清掉并可证明。
4. 「约束靠程序」：哪些检查可以用确定性程序做，哪些必须靠模型；模型只提议、程序校验提交的模式在大规模 wiki 维护里是否可行。

## F. 模型能力差异和引导方式
1. 文章说「告诉模型记忆用途、别规定用法」对强模型更好，而弱模型需要明确引导。我们会接多家模型、能力参差：有没有研究或实践支持「按模型能力自适应」的记忆引导和 harness 设计？如何在程序层兜底，使弱模型也不会把记忆写乱？
2. 主 Agent 会话中写记忆 vs 后台专职 Agent 写记忆，各有什么证据？我们目前是后者为主，是否应该给主 Agent 开放「显式记一笔 / 标记显著事件」的能力？

## G. 安全和隐私
1. 资料库文档里的提示词注入、记忆投毒（恶意或错误内容被提炼进长期记忆或 wiki 后长期生效），有哪些攻击研究和防护办法？
2. 本地优先下的隐私：哪些操作可以用云端模型、需要用户授权；敏感内容识别和隔离。

## H. 评测方法
1. 我们应该怎样建立自己的评测：从用户真实资料库构造问题集（单文档查找 / 跨文档综合 / 需要计算或判断 / 时间变化）、评分标准、指标（正确率、每题 token、延迟、花费、过期率、引用准确率），以及「整理轮数 → 效果」的曲线怎么测。
2. 哪些可以做成自动回归测试（我们的项目要求每个能力都有自动测试）。
