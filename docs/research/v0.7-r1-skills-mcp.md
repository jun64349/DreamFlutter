## 2. Agent Skills 规范与官方创建器

标准目录是 `<name>/SKILL.md`，可带 `scripts/`、`references/`、`assets/`。YAML 必填 `name`、`description`：名称 1–64 字符、小写字母/数字/单横线、首尾无横线且与目录名一致；描述 1–1024 字符并说明用途和触发条件。可选 `license`、`compatibility`、`metadata`、实验性的 `allowed-tools`。`allowed-tools` 不能越过应用真实审批规则。[Agent Skills 规范](https://agentskills.io/specification)

三级加载为名称/描述目录 → 命中后正文 → 按需引用/脚本。官方集成指南给出的目录成本约每技能 50–100 tokens，正文建议小于 5,000 tokens；不是每次把所有正文塞进系统提示词。[官方集成指南](https://agentskills.io/client-implementation/adding-skills-support)

官方 **skill-creator** 的可借鉴点是先明确用途、形成技能、使用真实任务做有/无技能或旧/新版本对照、检查产物、按反馈迭代；另用正负触发样本校准描述。我们的首版只需小样本、产物断言和用户确认，不引入它整套评测平台。[官方 skill-creator](https://github.com/anthropics/skills/blob/main/skills/skill-creator/SKILL.md)

官方 **mcp-builder** 以服务文档研究、实现、构建/Inspector 测试、业务任务评测四阶段组织。新服务要有清楚的输入输出、分页和错误；连接成功与实际完成任务分别验证。上游当前区分 SDK v2 与既有 v1；不能混用例子，也不能因此自动升级 Pi。[官方 mcp-builder](https://github.com/anthropics/skills/blob/main/skills/mcp-builder/SKILL.md)

## 4. MCP Registry 的实际查询契约

Registry 只提供元数据，软件仍来自 npm/PyPI/镜像或服务商；收录和命名空间验证不等于平台替其安全性背书。[官方 Registry 说明](https://modelcontextprotocol.io/registry/quickstart)

发现流程建议使用：

```text
GET https://registry.modelcontextprotocol.io/v0.1/servers?search=filesystem&limit=10
GET /v0.1/servers?search=filesystem&limit=10&cursor=<上一页 metadata.nextCursor>
GET /v0.1/servers/{encodeURIComponent(serverName)}/versions
GET /v0.1/servers/{encodeURIComponent(serverName)}/versions/latest
GET /v0.1/servers/{encodeURIComponent(serverName)}/versions/{encodeURIComponent(version)}
```

按返回的 `servers[].server` 和 `_meta` 读取版本、状态、包/远程地址，排除删除项、提示 deprecated；固定选中版本，不静默跟随 latest。cursor 原样传递，到空结束；搜索是服务名子串，不是全网语义搜索；官方当前对非空搜索要求 trim 后至少 3 个 Unicode 字符。需要按功能搜时同时查服务商官方文档。[通用 API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/generic-registry-api.md)、[官方 API](https://github.com/modelcontextprotocol/registry/blob/main/docs/reference/api/official-registry-api.md)

本轮真实 GET 的成功/失败、脱敏响应另存 [查询证据](v0.7-t72-evidence/registry-probe.json)。查询无需凭据；只读查询不连接/启动所列的第三方服务。

## 5. Inspector 与现有 Pi 的版本边界

**重要兼容发现**：本仓库锁定 `@earendil-works/pi-mcp@1.4.0`，本地 README 的 Supported protocol surface 明示 `2025-11-25`，接受更旧协商版本。该版本采用 `initialize` → `notifications/initialized` → `tools/list`。而本日官方 latest 指向 `2026-07-28`，其 modern 协议不再使用初始化握手，改为请求级版本元数据与 `server/discover`。因此 T-73 的“握手”应以 **当前 Pi 支持的协议** 实测；modern-only 服务明确报不兼容，升级属于后续技术决定。本任务不修改现有契约。[2025-11-25 生命周期](https://modelcontextprotocol.io/specification/2025-11-25/basic/lifecycle)、[当前版本规则](https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning)

Inspector 当前主分支文档也已描述 v2，应在实施时固定已验证的 npm 版本。建议用 CLI 做一次性连接与退出，不把 Web UI 和完整调试环境随包带入。

```text
npx @modelcontextprotocol/inspector@<已验证版本> --cli --config <临时配置.json> --server <服务名> --method tools/list
npx @modelcontextprotocol/inspector@<已验证版本> --cli <服务URL> --transport http --method tools/list
```

以上是命令模板，本轮没有安装/执行 Inspector，没有调用真实第三方 MCP 工具。配置应引用临时环境中的服务和测试凭据，避免把 Key 写在命令行/报告。旧 SSE 即使 Inspector 能连，也不代表产品支持。服务测试以真实 Pi 客户端为主、Inspector 为独立排障辅助。[Inspector CLI 官方说明](https://github.com/modelcontextprotocol/inspector/blob/main/clients/cli/README.md)

| 步骤 | 输入/操作 | 判定与失败回执 |
| --- | --- | --- |
| 需求澄清 | 任务、输入输出、工作台/蝶君、联网/Key、代表性样本、可接受效果 | 需求足够可测；缺关键资料才提问 |
| 先搜成熟方案 | 按 §3 搜 2–3 个可用候选并比较来源、许可、依赖 | 有适配方案就推荐复用；自建须有用户明确独特设计指令，不能伪造检索结果 |
| 隔离暂存 | 获取固定版本完整目录；社区/Agent 新建默认未信任 | 不直接启用、不在本机试跑未知脚本；更新不能绕过再次确认 |
| 静态测试 | 真 YAML 解析；字段/目录名；引用存在且在技能根内；脚本解释器/平台、依赖与可执行性；脚本路径无越界 | errors=0 才过；warnings 单列。Windows Python 脚本不以 Unix +x 作为必要条件；语法通过不等于任务通过 |
| 沙箱任务验证 | 一正例、一邻近负例；按派工允许的测试范围在蝶君临时目录执行，受超时和有限输出控制；产物重开/断言 | 对输入输出逐条断言；未信任脚本不在本机执行，沙箱测试不自动授信或启用。拒绝/缺依赖/超时分别回执 |
| 登记待确认 | T-73 接口写来源、版本/hash、测试时间、支持环境、结果、目标工作区 | 返回稳定条目 ID 与 pending；Agent 不能自己授信或授予蝶君 MCP 权限 |
| 用户启用与复核 | 用户确认后启用；刷新会话目录，再做一次命中加载 | 记录实际加载次数/最后时间，不依赖模型自报；关闭后自动路由不可再见 |

测试复用现有安全规则和派工范围，不新增一套审批流程。官方技能也须在当前工具名、沙箱路径和平台上验证，不能仅以创建器输出“看起来正确”判过。

## 7. 落到“建 MCP”的步骤与通过标准

1. 明确要读/写什么服务、在哪端使用；先查服务商官方文档和 Registry，优先配置成熟服务。没有适配才设计一个有边界的适配器，不把“接上服务”扩张为全部 API。
2. 校验固定版本、许可、运行命令/URL、参数 schema、鉴权方式；工作台本地服务走现有最小环境与审计，密钥继续存 SecretStore。生成配置也先 pending，不能自授信。
3. 对用户允许测试的服务做**临时真实连接**，使用当前 Pi 协议初始化、能力判断、完整分页 `tools/list`，收集名称/描述/schema；最终关闭连接和子进程。超时、鉴权、命令不存在、协议不兼容、无工具、取消、清理失败分别返回。
4. 连通通过：连接/初始化成功、工具响应可解析且符合声明、清理完成、耗时可查。没有 tools capability 的合法资源服务可记“连接成功但不满足本次工具需求”，不谎报坏服务或业务验收通过。
5. 业务通过：选择一个已知答案的只读任务，核对结果/错误回执；写工具在工作台仍走既有审批。`tools/list` 通过不能冒充业务调用、账号权限、网络稳定性全部通过。
6. 写入测试报告与来源，等待用户确认启用；蝶君每服务独立授权，默认全部关闭。测试成功不是信任授予。

建议测试报告最少含 `target/version/transport/protocol/status/durationMs/tools/errorCode/redactedReason/cleanup`；这是信息要求，不强制 T-73 改成这些字段名。连接成功、业务成功、格式通过、信任与启用保持各自状态，界面只展示现有技能页所需信息。
