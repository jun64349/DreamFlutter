# R4：安全现状、成本与 v0.6 建议范围

查询日期：2026-11-07（Asia/Taipei）；T-60，只读，基线 `deb6224`。依据 [原安全调研](agent-security.md) 的 P0–P3 和 [HANDOFF](../HANDOFF.md)；原文保留，不就地改写。本轮是静态核查，不是渗透测试或“安全已通过”认证。

## 结论

建议本版优先做 **P0 两项 + P1 两项**，并为这些动作补最小审计字段。P2 Windows 原生隔离和全进程出站白名单先不纳入本轮实现，继续利用已存在的 WSL 隔离并验证其边界。P3 不开展企业遥测或不可篡改日志系统。范围和例外策略交用户与 Claude 确认后派工。

现有系统已有审批、沙箱、密钥加密、部分脱敏和记忆安全扫描，不能重复描述成“完全没有安全”；同时也没有证据证明这些局部措施覆盖了所有工具、shell 和 MCP 数据流。

## 逐项矩阵

成本是相对工程规模：小=局部策略/记录；中=跨工具/配置/测试；大=操作系统与进程生命周期或网络强制执行。不是工期承诺。

## 原调研需要纠正的地方

1. 原文把 `cargo check` 举作明确只读命令不妥：它可能执行构建脚本并写构建产物，不进入免审批白名单。AST 能识别语法，不能证明程序没有副作用；外部命令及参数语义仍需约束。
2. “彻底堵死提示注入/密钥泄露”过强。网页、文件、MCP 输出均可能夹带指令；分层校验、最小权限和人工审批降低风险，但不构成绝对保证。[S3]
3. WSL 已是既定实现，原文再把 Docker/WSL 当未选备选已过时。本版不扩展新容器产品线。
4. 旧卡片路径 TOCTOU 和短于 8 字符 key 脱敏例外属于已记录限制；本轮没有新利用证据，不能升级成已复现高危漏洞。若进入本版，先写可重复回归样本再决定修复范围。
5. “结构化”不等于“不可篡改”。本地 JSONL 仍受同用户权限影响，不因此宣称企业审计合规。

## 建议授权边界

**方案 A（推荐）**：P0 路径策略、保守命令判断；P1 日志/输出脱敏与 MCP 最小环境；同步补最小审计和现有 WSL 自检。路径策略明确区分默认拒绝、需确认及允许，默认策略不得被模型文本修改。具体默认目录和例外是否跨会话保存由 Claude 写契约后确认。

**方案 B**：只补已知密钥日志脱敏与审批漏洞回归，其余延期。改动小，但普通文件工具对敏感路径的缺口继续存在。

**方案 C**：A 加 P2 原生隔离和全出站控制。保护范围更大，但涉及系统级行为、性能、工具兼容和前端解释，不推荐在本版直接全包。

在 A 下，真实密钥不用于测试；用合成 canary。验收至少覆盖路径别名/链接、工作区普通读写、`.env.example` 误拦、命令替换/重定向/别名、审批取消、日志异常堆栈、分块输出、MCP 所需变量、代理密码、离线沙箱绕过尝试。现有 tests 通过也不能代替这些专项。本轮**未运行**。
