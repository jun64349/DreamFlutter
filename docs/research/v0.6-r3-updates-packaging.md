## 成熟方案对比

| 方案 | 官方做法/能力 | 对 DreamFlutter 的判断 |
| --- | --- | --- |
| VS Code Windows | 用户安装器支持后台更新并重启生效；也提供 ZIP 交付。[U1] | 借鉴用户级安装、下载与激活分离；不能推定 ZIP 自动获得同样的安装更新保障。 |
| Velopack | 桌面安装/自动更新工具链、打包与分发机制，支持代码签名。[U2]、[U3] | 候选优先验证；官方入口列多种 SDK，但没有本轮已验证的 Flutter 直连方案。需要桥接、进程生命周期与 Node/WSL 兼容验证；数据迁移回滚仍由应用负责。 |
| MSIX + App Installer | Windows 提供更新检查/修复与安装策略。[U4] | 较强系统管理，但包身份、签名、路径及当前 WSL/可写数据布局需要专项适配，v0.6 不建议直接迁移包装方式。 |
| Electron autoUpdater | Windows/macOS 更新能力依赖平台及打包方式。[U5] | 仅作为流程参考；本项目是 Flutter，不引入 Electron 作为更新依赖。 |
| 自管 portable + 外部 helper | 项目自行处理下载、校验、退出、目录切换、恢复。 | 与现有目录形式接近，但故障矩阵和维护成本高；不能仅以 PowerShell 覆盖文件作为完成。成熟更新器不适配时才进一步评估。 |

## GitHub Releases 源

官方 REST `GET /repos/{owner}/{repo}/releases/latest` 可无鉴权读取公开仓库的正式发布；排除草稿/预发布。响应含 `tag_name`、发布说明、附件名称/大小、`browser_download_url`，文档示例含 `digest: sha256:…`。[U6] 当前仓库远端为 `jun64349/DreamFlutter`。

建议按平台/架构/包类型精确选择附件，解析语义版本，不取“第一个 asset”，也不把源码 zip 当程序包。404（没有可用 Release）、离线、限流、无匹配附件和已是最新版应分开。公开 REST 未鉴权限额通常每 IP 每小时 60 次，检查应缓存、退避，不能随窗口重绘轮询；不在公开客户端捆绑发布 token。[U7]

哈希校验用于完整性，**不替代发布者签名**。下载域可能经 GitHub CDN 跳转；信任范围需显式设计，不接受任意更新 feed 指向的执行文件。测试源仅本地开发配置，不让网页内容任意改更新源。

## 建议更新流程（待实现）

1. 检查版本、架构、兼容版本和发布说明；前端沿用现有设置/关于入口，新增交互由 Claude 确认。
2. 下载到临时目录，验证实际大小/哈希；验证签名链及预期发布者。Windows SignTool 支持签名与验证，发行签名材料需独立管理。[U8] 缺可信签名的生产包不静默降级；本地测试证书只用于隔离测试。
3. 用户开始安装前，停止新任务并等待/停止在途工作，关闭数据库写入；复用备份模块取得一致备份，验证可读和空间足够。不能只复制一个正在写入的 SQLite 主文件而遗漏 WAL 状态。
4. 外部更新进程在应用退出后将新版本放入新目录；保留旧版本、备份及明确的更新阶段记录。重启时能识别上次中断，不循环覆盖。
5. 启动新版本，验证 Core 握手、数据库迁移和数据路径；成功后才清理临时/旧版本。失败回旧程序，必要时在新版本尚未对外接受写入前恢复配套数据备份。
6. 一旦新版本已接受用户新写入，不能直接恢复旧备份并丢弃新内容；应停止写入、保留失败现场和新数据，进入恢复流程。二进制可回滚不代表数据库可降级。

上述是工程建议，不是现有功能声明。T-62 的路径搬迁/备份与更新器需共用一个数据来源，不各造一套备份目录和密钥迁移规则。
