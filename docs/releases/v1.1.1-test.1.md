## 发送和流式输出

用 Windows 工作台的 DSH 会话，在重启本地后台后向同一个中转渠道连续发送七次。每次让本地传输返回同样的短句，真实运行 Windows 凭据解密和梦蝶的会话、工具、账本及事件转换。下面统计从发送指令到后台发出首个文本片段的时间。

| 条件 | 修改前 | 修改后 |
| --- | --- | --- |
| 本轮试跑重启后的第一条 | 606 毫秒 | 499 毫秒 |
| 随后六条 | 292–481 毫秒 | 27–35 毫秒 |
| Windows 解密执行次数 | 七条执行七次 | 七条共执行一次 |

梦蝶在进程内复用自己管理的渠道凭据。两个会话同时首次使用同一把钥匙，共享正在进行的解密。用户替换密钥后，下一次请求使用新密钥。逐次解析的外部凭据引用继续由原提供方管理。选中一个渠道发送请求时，按该渠道查询配置，避免逐一解析已配置的所有渠道。公网延迟、模型推理耗时及真实服务的排队时间均未纳入本次数字。

在工作台组件测试中固定模型等待为 224 毫秒，每 16 毫秒检查一次画面。首个文本片段到达后，可见文字从 48 毫秒提前到 16 毫秒。18 个连续片段中，下一帧已可见的从 6 个增至 18 个。输入框、侧栏和历史窗口在纯文本流期间的整窗通知从 6 次降到 0 次。

160 条历史消息的 Windows 实窗中，连续输出文字时 Flutter 构建耗时 P95 的两次基线为 7.65、6.92 毫秒，流式更新优化后为 2.83、2.84 毫秒。修复旧行重新进入视野时的入场动效后，最终复测为 **2.57、2.61 毫秒**。对应整帧 P95 从 20.23、16.90 毫秒变为 17.28、16.85 毫秒。边输出边打字还没有测得稳定改善。首页从约 83–103 帧/秒提高到约 109–110 帧/秒。开发工作树内的[窗口帧时间记录](../testing/v1.1-windows-frames.md)包含原始数据、机型和复跑方法。

## 工具执行中止与恢复

用真实 PowerShell 启动一个等待中的 Node 子进程，分别从标准工作台、轻量工作台和子代理执行，再走产品的取消入口。三条路径均结束了父子进程。从发出取消到收到结算并验证进程退出，两轮分别为 215 / 168 / 207 毫秒和 858 / 501 / 501 毫秒，第二轮有并行测试负载。之后可以继续发送消息、运行工具并收到回复。

连续多步工具调用会逐步检查已有的轮数与预算限制。连续读取同一内容、结果没有变化时会提醒换方法。正常读取不同资料仍能继续。
