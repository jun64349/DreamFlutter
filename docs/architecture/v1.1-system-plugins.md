# V1.1.0 内置系统插件迁移对照

用户在 2026-11-20 确定，V1.1.0 要把现有平台迁到官方 DeepSeek Harness。已有功能尽量作为系统插件随程序内置，安装和启动梦蝶时自动装配。版本范围见 [开发计划](../roadmap.md)，实测进度见 [交接记录](../HANDOFF.md)。

## 从现有功能逐项接过去

功能范围见 [开发计划](v1.1-development-plan.md)，成品和测试结果见 [交付记录](../releases/v1.1.0.md)。记忆通过数据目录的 `system-plugins.json` 选择是否加载，修改后重启生效。省略该文件会装入记忆；将 `dfMemory` 设为 `false` 会停止装配其服务、快照、工具和整理任务。备份继续保存旧数据。

下面登记的是 1.0 现有实现和迁移时要实际走通的入口。启动装配要同时对照 [buildCore](../../core/src/app.ts) 和 [Core 构造与会话钩子](../../core/src/core.ts)。构造时注册接口的服务、直接挂在 Core 上的服务也要登记。固定系统插件由随包清单装配，按依赖启动，退出时释放各自持有的资源。

| --- | --- | --- |

Windows 工作台和蝶君沿用原窗口协议。新对话由 DSH 写入 JSONL。窗口继续按文件路径、父子关系和记录类型查历史。1.0 旧对话保留原件，点「继续」以后另开 DSH 会话，带入所选分支上文、工具结果和附件。对应的历史样本与断言见[工作台契约测试](../../core/test/api-contract/dsh-workbench.test.ts)。

## 蝶君替换 Linux 的验收

1. 从全新的 Windows 数据目录启动蝶君，不依赖已注册的 WSL 发行版。隔离进程能在私有工作区内收资料、执行工具并交付文件。
2. 使用合成的外部文件及只读工具样本分别验读和写。离线、允许联网以及本机服务访问要分别有对照。任务结束后核对子进程退出、打开的文件能释放。
3. 用随包的实际工具跑办公样本，查看生成的产物。核对 Python、Git、搜索、渲染和各自的缓存/临时路径，避免某项工具在新工作区失败后悄悄回到宿主运行。
4. 分别从工作台、蝶君、新安装和升级入口检查。现有 WSL 沙箱备份支持把 `/workspace` 和 `/home/agent` 打入归档，需显式包含沙箱；常规数据副本未必包含这两处。用合成旧环境验可恢复的数据及失败回退，再替换安装、迁移、重置和卸载流程。

窗口协议以 [现有接口清单](../api/README.md) 和 [契约测试](../../core/test/api-contract) 为准。V1.1.0 仅交付 Windows。macOS 的新后台迁移安排在 V2.0.0 完成之后。

## 官方内核怎样随梦蝶更新

安装包携带 Node、DSH、Cordis、系统插件以及运行依赖。桌面窗口经本机连接调用梦蝶后台，后台在自己的进程里加载这些包。使用云模型时，模型请求仍按用户选定的渠道发送。DSH 上游发布与梦蝶用户升级是两件独立的事。

1. 在开发工作树中选定一组上游版本，核对发行说明和存储格式变化。用精确版本更新 `core/package.json` 与 `core/package-lock.json`，从锁文件执行 `npm ci`。两个已上架包的 `engines.dsh` 和 `peerDependencies` 也固定到实测版本。对新内核分别复跑用量统计和窗口快捷键，在确认兼容后更新它们的清单及目录版本，再用旧安装的启停状态复验升级。若上游接口变动，先修复 [DSH 适配代码](../../core/src/dsh)，保留窗口已有的消息和权限行为。
2. 在 `core` 目录运行 `npm run typecheck`、`npm run verify:dsh`、`npm run test:dsh-upgrade`。这些检查覆盖正式运行包的加载、历史续写、带图片的工作区迁移、窗口协议、模型组、预算、工具权限和数据备份。Windows 原生工作区另跑 `test/appcontainer-runner.test.ts`、`test/appcontainer-provider.test.ts`、`test/dsh-appcontainer-tasks.test.ts` 和 `test/dsh-appcontainer-workloads.test.ts`。给这些测试的 `DREAMFLUTTER_APPCONTAINER_TEST_PACKAGE` 指向解包后的 DreamFlutter，`DREAMFLUTTER_APPCONTAINER_TEST_NODE` 指向该包的 `runtime/node.exe`。窗口插件通过 `flutter test integration_test/v11_plugins_test.dart -d windows` 从真实界面验证。
3. Windows 打包脚本用成品里的 Node 重跑版本和历史检查，再分四次启动成品后台，通过与窗口相同的接口调用本机模拟模型。检查覆盖插件安装、原会话续聊、记忆停用及恢复、旧历史和备份。缺包、依赖版本偏离锁文件或重启后缺少上文都会使构建失败。历史样本使用合成数据，升级时保留原样本，新增格式另存一份。[依赖和历史检查](../../scripts/verify-dsh-runtime.mjs) · [成品工作台试跑](../../scripts/verify-dsh-workbench.mjs) · [固定样本](../../core/test/fixtures/dsh)
4. 用上一版数据的副本试升级、备份恢复和回退，再按项目既有发布流程交付。升级失败时恢复与原程序匹配的升级前备份。已经用新版本写入的会话需要经过单独的向后兼容验证，才可交给旧程序打开。
