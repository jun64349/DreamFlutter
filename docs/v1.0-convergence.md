# v1.0.0 收敛说明（开发 Agent 必读）

记录日期：2026-11-06。

用户在本次讨论中明确表示：**现有 v1.0.0 开发计划的功能已经比较满足自己的设想和需求，同意在这个基础上控制新增范围，推进完成和稳定使用。** 本说明落实这一决定，适用于后续开发、调研、审查和交接。

## 一、范围以什么为准

- 功能范围以本说明写入时 [roadmap.md](roadmap.md) 中已经确认的 v1.0 及之前的计划为基线；具体行为以已定稿的 [memory-design.md](memory-design.md)、[long-task-design.md](long-task-design.md) 和用户已经确认的决定为准。
- 继续原定路线：0.5–0.9 后端和必要界面 → 0.10 接口文档 → 0.11 前端整合 → 0.12 打磨与深度测试 → v1.0.0。不要借收敛另排一套架构或开发流程。
- **冻结的是新增产品范围，不是冻结实现。** 计划内尚未完成的功能继续完成；修复、必要的实现机制、兼容处理和验收工作继续做。
- 不得以收敛为由，擅自删掉、推迟或降低已经答应的功能。确实存在无法兼容的要求或必须调整的产品范围时，说明具体冲突，再由用户决定。
- 用户以后明确提出的新要求可以改变基线；更新对应文档并写清影响。Agent 的建议、调研中的发现、参考项目的新能力，不自动成为新需求。

## 二、遇到新想法时怎么判断

先问：**“不做它，会不会导致现有计划里已经答应的功能无法正常使用，或无法满足已定的行为约束？”**

| 情况 | 处理方式 |
|---|---|
| 实现已计划的功能 | 按原计划继续做，补清支持范围和验收依据 |
| 已有承诺无法兑现、出现错误或回归 | 修复；用实际问题和适当验证说明必要性 |
| 为满足原有承诺必须补充内部机制 | 可以做；说明它服务于哪个条目，以及现有机制为何不足，选择足够解决问题的实现 |
| 能让产品更强、更通用、更聪明，但不影响已有承诺成立 | 记入 1.x 待办，不顺手塞进当前版本 |
| 因为参考项目有、未来可能用到、设计上更完整而提出的新机制 | 同样留作后续考虑，不视为当前版本的前置条件 |

例如，为兑现“停止后不自动续跑”而补充状态检查，属于必要实现；再增加一种自主行为或一套独立调度方式，不能仅凭“以后会更好”进入 v1.0.0。不要把增强项改称“基础设施”“安全补强”或“重构”后绕过范围判断，必要性要能对应具体承诺或问题。

常规实现选择和范围内修复由开发 Agent 正常推进，不必把每个内部机制都变成用户审批。现有提交、打 tag、推送等协作约定照旧。

## 三、把宽泛功能做成有边界的首版

“办公能力”“建技能和 MCP”“自主工作和学习”不能被理解为覆盖所有格式、服务和任务。按原计划在对应版本的设计中明确：

- 支持什么输入、操作和输出，以及依赖的环境；
- 怎样验证成功，失败、缺条件和不支持时怎样说明；
- 哪些具体能力属于这次交付，哪些留到以后。

这些边界写入已有设计、测试清单或发布说明即可，不另建一套管理系统。原计划仍需用户定的产品选择照常确认；不要擅自承诺全能，也不要擅自缩减已确认范围。

真实模型能做成一组代表性任务，就按这组任务的证据评估；不要把“任意任务都成功”“永不误记”“能无限自主推进”当作发布条件。原有约束仍必须成立：该停止时停止，失败和阻塞如实报告，不能用模型说“完成”代替产物和验收。

## 四、后续开发重点

1. **复用已定的共同规则。** 继续遵守 roadmap 的唯一调度者、结构化状态、带版本的准备与启用、停止优先、真实回执和统一账本。发现冲突时修接入和职责，不为每个模块再造一套平行机制。
2. **0.8 是关键整合点。** 重点验证记忆、压缩、子 Agent、定时任务如何接入目标服务；停止、插话、预算、等待和恢复的核心行为应验证后，再让 0.9 的自动执行依赖它们。不要用自主规则掩盖调度问题。
3. **后端优先仍要走通真实流程。** 各版的最简界面要支持对应功能的使用和验证；按计划持续验证“提出需求 → 执行 → 查看产物 → 修改要求 → 停止或恢复”，不要把跨模块问题全留给 0.11。
4. **必要控制与自动能力一起交付。** 例如记忆默认自动生效，对应的最简日志、纠正和撤销入口也是计划内功能，不能当成可无限后移的美化。
5. **0.10、0.11、0.12 以整合和收尾为主。** 接口文档暴露的问题要修，前端要把既有能力接通，深测要消除影响使用的问题；不要在这些阶段主动塞入新一轮能力扩张。
6. **轻量化是实现约束。** 用户补充要求平台大小尽可能轻，已纳入 roadmap 的 6.14、0.7 依赖检查和 12.5；不另加版本。优先精简打包冗余、复用依赖和解释体积增长，保留已确认功能、随附沙箱镜像及离线可用承诺，不为减重另建机制或追求任意大小指标而无限延长开发。

## 五、怎样判断接近发布

“代码已写”“测试通过”“用户能正常使用”分别记录，不能互相替代。沿用 [testing/scenarios.md](testing/scenarios.md) 和现有测试流程，在相关版本及时补入新场景、修正已经过时的描述。

发布前应能给出以下证据：

- 计划内功能有明确的完成状态和验收依据，尚未完成的如实列出；
- 用户能从界面走完关键流程，产物能打开，状态、费用和提示与实际一致；
- 关键组合场景经过验证：后台工作与用户修改同时发生、停止时完成事件返回、压缩与纠正交错、重启恢复、升级与备份恢复等，按各功能的适用范围测试；
- 代表性任务经过真实模型验证，安装包经过实际环境验证；假模型测试不代替模型效果和安装包可用性；
- 发布前明确必须修复的问题及理由。数据丢失、越权、停止失效、重复执行有实际后果的操作、核心流程不可用，应作为阻塞候选重点处理；可接受的限制写清楚，沿用原计划由用户最终验收。

成功率、性能、费用和观察时长等需要阈值时，根据代表性任务、实测数据和用户要求确定，并在最终验收前明确；本说明不凭空规定数字，也不新增一套必须开发的评测平台。

不要在每轮测试后不断提高完成标准。新增问题先判断是违反既有承诺的缺陷，还是新的增强需求，再按 roadmap 0.12 的“1.0 前必须修 / 1.x”分类。

## 六、交接与后续想法

- 在现有交接中写清：本轮完成了什么、验证了什么、还缺什么，以及是否出现需要用户决定的范围冲突。文档记录不能把旧测试结果当作新改动的验证。
- 对暂不纳入的新想法，简短记录在现有文档的待办或 roadmap 的“1.0 之后”部分，标明“未纳入 v1.0.0，尚未承诺”；不需要展开设计，也不要让它成为当前版本的新依赖。
- 向用户报告进度时，优先说明已有功能是否接通、异常能否恢复、验收还缺哪些证据，避免把新增机制数量当作进度。

当前目标是把已经确认的产品做完整、做稳定。完成既定范围并验证可用之后，允许 v1.0.0 结束开发、进入发布。
